# Sealer load bench: decision version 3 (2026-10-20)

The baseline of the sealer before decision version 4. Commit `9b0a4a18`, `just sealer-bench`.

## Setup

- One host: 12 cores, 62 GiB. Other work ran on the host, and the load average was 11 to 26. All members share the host over loopback, so the latencies are upper bounds.
- Two twins offer the same records in batches of 64. 4096 senders take turns, so each sender's nonces arrive in order.
- One consumer reads the canonical stream. The latency runs from the due time of a batch to the relayed frame at the consumer.
- Each run has 3 s of warm-up and 10 s of measure, unless the table says otherwise.

**Staging settings:** blocks of 2000 ms, a horizon of 64 blocks, a window of 131,072 ids, and `-Xmx384m -XX:+UseSerialGC`.

**Engine settings:** blocks of 250 ms, a horizon of 8 blocks, a window of 4,194,304 ids, and `-Xmx2g -XX:+UseSerialGC`. These settings remove the window cap, so the runs show the cost of the record path.

## Staging settings, 3 members

| Rate per twin | Relayed/s | p50 | p99 | Max | Rejects |
|---|---|---|---|---|---|
| 500 | 493 | 6.0 ms | 33.6 ms | 74.6 ms | 0 |
| 1,000 | 998 | 6.0 ms | 32.0 ms | 51.0 ms | 0 |
| 2,000 | 1,997 | 5.5 ms | 30.4 ms | 61.4 ms | 0 |
| 5,000 | 4,998 | 5.2 ms | 14.9 ms | 72.2 ms | 0 |
| 2,000 for 90 s | 1,456 | 5.4 ms | 31.5 ms | 217.6 ms | 48,832 window-full per twin |

In the 90 s run, the sealer ordered exactly 131,072 records, and then refused every record as window-full.

- The window holds an id until its deadline.
- The ingress stamps a deadline 64 blocks ahead, and a block is 2 s, so an id stays 128 s.
- So the window frees about 1,024 ids each second.

**On staging, decision version 3 sustains about 1,000 tx/s.** A burst above that rate fills the window, and the sealer then refuses records.

"Saturated" means that the twins fell behind their schedule. The latency then grows with the run, and its percentiles have no meaning.

- **The ceiling.** Three members saturate at about 76,000 relayed tx/s, and one member at about 200,000.
- **The lagging twin.** When one twin lags by more than the horizon, its copies have left the window. The contiguity guard then refuses them, and they are not ordered twice.

## Profile

This is a JFR profile of one member at the maximum rate.

- The service thread has 85% of the CPU samples.
- `CanonicalSealerState.onRecord` has 41.5%, and the deadline prune at each tick has 14%.
- Hash map work is about half of the samples. Most of it is in tree bins of the id map.
- The tree bins did not appear offline. The same ids in the state alone gave 732,000 records/s on one thread, with no tree bin. So the cluster numbers can understate decision version 3.

## Conclusions

1. **Staging cap.** On staging, the id window caps the sealer at about 1,000 tx/s sustained.
2. **The engine limit.** Without the cap, the service thread limits decision version 3 to about 76,000 tx/s with 3 members on this host. The id map, the deadline map and the allocation of each record are the cost.
3. **GC pauses.** SerialGC pauses of 0.2 to 0.7 s set the tail latency.

Decision version 4 removes the id map, the deadline map and the allocation of the record path.
