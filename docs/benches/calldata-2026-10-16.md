# Calldata bench: baseline of main, 2026-10-16

- Build: `main` at `815ff48c` with the bench tooling of this change. The sealer orders references (no transaction bytes in the Raft log).
- Cluster: the local container cluster (`just container-reset`), a fresh chain. All nodes share one host, so the numbers compare builds. They are not absolute.
- Host: 12 CPUs, 63 GiB, load average at start 10.06 9.55 13.50
- Each cell: warm-up 60s, then 300s measured, 15 senders, `--fixed-rate --subscribe --max-in-flight 4096`. Offered tx/s is the offered count over the measured time.
- Calldata: the calldata bytes of each transaction. The raw size is about the calldata + 110 bytes. `a:w,b:w` is a weighted mix.
- Receipt latency: `kardamom-load`, p50 / p99 in ms. Seal latency: `kardamom_ingress_seal_latency_seconds` on ingress-0, p50 / p99 in ms, interpolated in the histogram buckets.
- Leader CPU: `docker stats` of the leader node container every 5 s, mean / max in % of one CPU.
- Snapshot: the largest `ms=` of the `sealer snapshot TAKEN` lines of all members in the measured part, and the line count.
- Host load and host CPU: the 1-minute load average at the end of the cell, and the busy % of all host CPUs in the measured part.

## Scope of this run

The run covers the rates 250 and 500 tx/s at the three sizes, and 1,000 tx/s with no calldata. The full matrix of the spec (500 to 6,000 tx/s, and the 5,000 tx/s rows) did not run, for these reasons:

- On this host, the cluster does not hold 500 tx/s at 8 KB. The 1,000 tx/s cell with no calldata passes, but its receipt p99 is 2.5 s. Higher rates only fill the queues.
- A cell that overloads the cluster can stall the next cells. In an earlier run on an older chain, the sequencers evicted transactions at 1,000 tx/s. After that, the sequencer expected a nonce below the nonce of the chain for some senders, and every later transaction of those senders expired. Only a fresh chain removed the stall. The script now gives each load its own transfer value, so two loads never sign the same transaction. This run puts the cells that can overload last in each size.

Run the full matrix with `just bench-calldata` on a host with more free CPU. `RATES`, `SIZES` and `EXTRA` select the cells.

## Findings

- The host is noisy. The 1-minute load average is 17 to 36 on 12 CPUs, and the host CPU is 54 % to 80 % busy. Most of the load is the busy-poll threads of the cluster itself.
- The seal latency is most of the receipt latency in every cell that passes. The p50 values agree within 10 ms.
- The latency grows with the size at a fixed rate. At 250 tx/s the receipt p50 is 30 ms with no calldata, 32 ms at 2 KB and 95 ms at 8 KB.
- At 500 tx/s and 8 KB (about 4 MB/s of transactions), the load offers only 351 tx/s. The seal p99 is above 5 s, and 10,747 transactions get no receipt. On this host, the references build reaches its limit between 2 MB/s and 4 MB/s of transaction bytes.
- The leader node container uses about 30 % of one CPU in every cell. It does not grow with the rate or the size: the sealer orders references, so its work does not depend on the size.
- The snapshot takes 42 ms to 156 ms. This is far below the bound of 2 s.

## Not measured in this run

- The CPU of each thread of the leader, the GC pauses, and the fsync time.
- The network bytes of each member. The container cluster cannot measure the network limit, because its traffic never leaves the host.
- The retained file and the feed lag. These come with the bytes build.
