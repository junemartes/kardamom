# 02 f2accb1 — feat(sequencer): P=2 racing replicas per shard (no-stall sequencer failover) (#75)

## Summary of change
Each of the 2 sender-shards is now served by two active/active sequencer replicas on different nodes. Both consume the shard's tx_data multicast stream, deterministically emit byte-identical `TxRef`s, and both offer them to the Aeron Cluster, whose first-seen dedup on `canonical_id` (`TxRef.tx_hash`) keeps one. Implementation: a `--partition-offset` flag + `SequencerConfig::rotate_partition` so a second Nomad group (`seq-b`) serves the rotated shard from the same node-derived `--partition-index` (new `${meta.node_index}` node meta), guaranteeing the two replicas of a shard land on distinct nodes. Adds a 3-invariant integration test (`replicated_shard_racing.rs`), a `sequencer-replica-kill` chaos case, and a spec + failure-modes rewrite. Restart semantics are live-join only (no archive replay).

## Findings

### F02.1 [high] [logic] — Restarted replica never regains coverage: production hydrates nonce floors from `EmptyStateDatabase` (always 0), contradicting the commit's stated restart semantics
- **Where**: crates/sequencer/src/bin/kardamom-sequencer.rs:160,343-381 (`EmptyStateDatabase`, wired as the only `StateDatabase`); crates/sequencer/src/sequencer.rs:144-165 (`hydrate_if_unknown`); docs/agents/replicated-sequencer-shards-spec.md ("Restart / rejoin semantics"); docs/failure-modes.md:92-93. Same lines at HEAD (no commits touch `crates/sequencer` after f2accb1).
- **What**: The commit message, spec, and failure-modes doc all claim a (re)starting replica "hydrates nonce floors from committed state via the existing cache-miss path", and the new `cold_rejoining_replica_emits_a_suffix_and_changes_nothing` test seeds a `FakeStateDatabase` with the correct committed nonces. But the deployed binary wires `EmptyStateDatabase`, whose `basic()` always returns `Ok(None)` → every sender hydrates at nonce 0 (the in-bin comment admits this is only "sound for fresh chains"). Failure scenario: replica of shard 0 is killed and restarts (the exact `sequencer-replica-kill` chaos scenario). It live-joins mid-stream; every established sender's next tx has nonce k > 0, so `PartitionState::process` buffers it as "future" against expected 0 — and nonces 0..k-1 will never reappear on tx_data (live-join, no replay; they were already ordered/confirmed so clients won't retransmit). The restarted replica publishes nothing for any pre-existing sender, forever: it is a zombie, and the shard silently runs on one effective replica. A subsequent failure of the twin then stalls the shard even though Nomad shows 4/4 healthy allocs. Chaos cannot catch this: `assert_count` only counts allocs, `assert_progress` rides on the surviving twin, and each chaos case uses a fresh funded account (nonces from 0), which is the one case that works. The commit's headline guarantee ("restarts to full strength") holds only for redundancy against a *first* failure, not after any restart.
- **Still present at HEAD**: yes
- **Suggested fix**: Wire a real committed-state reader (read-only libmdbx snapshot / RPC to an executor) into the sequencer bin, or make hydration stream-adaptive (e.g., on observing nonce k for an unknown sender, adopt k as the floor after a confirmation probe / bounded wait — safe here because the twin plus cluster dedup make a duplicate ref harmless within the window). At minimum, correct the spec/failure-modes claims and add a chaos assertion that the *restarted* replica publishes refs again (e.g., its `tx_published_to_b_total` advances).

### F02.2 [medium] [logic] — Even with a real state DB, one-shot hydration races with in-flight ordering: cold rejoin can leave a per-sender gap that never heals
- **Where**: crates/sequencer/src/sequencer.rs:144-165 (`hydrate_if_unknown` — only consulted while the sender is unknown; `seed_next_nonce` once), crates/sequencer/src/state.rs:60-66; test crates/sequencer/tests/replicated_shard_racing.rs:206-230. Same at HEAD.
- **What**: Hydration reads the *committed* nonce c, but the twin may have already ordered nonces c..j-1 that are multicast before the rejoiner subscribed and not yet committed at hydration time. The rejoiner then only ever observes nonces ≥ j, which stay buffered as "future" against floor c; the floor is never refreshed (the cache-miss path fires only while the sender is unknown), and the missing nonces never reappear (live-join only; the twin ordered them so clients won't retransmit). Result: a permanent per-sender coverage hole in the rejoined replica (plus pending-buffer occupancy/eviction churn), i.e. F02.1's zombie effect persists in miniature even after the DB wiring is fixed. The test pins only the perfectly-aligned case (DB floor exactly equals the live-join point), which is the one alignment that cannot happen under load.
- **Still present at HEAD**: yes
- **Suggested fix**: Re-hydrate (or fast-forward) a sender's floor when its pending buffer holds a contiguous run strictly above the floor for longer than the commit latency bound, or periodically refresh floors for senders with non-empty pending buffers. Also extend the test to a misaligned floor (db nonce < join-point nonce) to pin whichever behavior is chosen.

### F02.3 [medium] [logic] — Double-ordering hazard: sealer's first-seen dedup window is 8192 ids, but a *live* replica's lag is unbounded
- **Where**: cluster/sealer-service/service/src/main/java/io/kardamom/sealer/cluster/ClusterNode.java:44 (`dedupCapacity` default 8192, FIFO-evicting per CanonicalSealerState.java:79-93); docs/agents/replicated-sequencer-shards-spec.md ("Non-goals": "live-join keeps re-offers inside the window"). Same at HEAD.
- **What**: The design bounds the restart case (no replay) but not the paused-replica case: a replica that stays connected but stalls (GC/CPU stall, SIGSTOP, cgroup throttling, Aeron receive backlog, or the sequencer's own backpressure retry loop) and resumes after its twin has pushed > 8192 *unique* canonical ids through the sealer will re-offer records whose ids have been FIFO-evicted — the sealer accepts them as fresh and the same tx is ordered twice in the canonical log. At even moderate throughput (e.g. 5-10k tx/s across the window) a ~1-2 s stall suffices. Downstream, the executor's own `DedupWindow` (crates/engine/src/reader.rs:219,228 — default 1<<20) will usually absorb the re-ordering for both `TxRef`s and `DepositRef`s, so the practical blast radius is canonical-log pollution and reliance on a second, differently-sized window rather than double execution — but the spec's safety argument ("re-offers stay inside the window") is simply not established for live laggards, and any canonical-log consumer without the 1M-entry window (validators, replay tooling) must replicate the dedup exactly.
- **Still present at HEAD**: yes
- **Suggested fix**: Bound replica lag relative to the dedup window: have the sequencer drop (not offer) records older than a freshness horizon after a detected stall (it can compare its tx_data position against live), or size/monitor the sealer window against worst-case stall x throughput and alert on `dedupSize` saturation. Document the invariant quantitatively in the spec.

### F02.4 [medium] [logic] — Metrics: per-shard sums double-count under P=2, seq-b's exporter is loopback-bound and scraped by nothing, and the spec's observability claims don't hold
- **Where**: deploy/cluster/nomad/sequencer.nomad.hcl:180-183 (`KARDAMOM_METRICS_ADDR = "127.0.0.1:9011"`; seq-a has no env at all → binary default `127.0.0.1:9001`, kardamom-sequencer.rs:81); crates/sequencer/src/metrics.rs:17-43 (only a `partition` label — no replica-group label); deploy/grafana/provisioning/dashboards-json/kardamom-sequencer.json (every panel is `sum by (partition)`); deploy/prometheus.yml:16-19 (no :9011 job anywhere in the repo). Same at HEAD.
- **What**: Both replicas of a shard process every tx of that shard, so `tx_ingested_total`, `tx_published_to_b_total`, `tx_dropped_past_total`, etc. now exist twice per `partition` — from *different hosts*, so the `host_id` label does not separate replica groups of one shard either. Every Grafana panel (`sum by (partition)`) reports 2x the real per-shard rate the moment both replicas are scraped; the dashboard was not touched by this commit. Meanwhile the opposite problem hides it today: seq-b binds 127.0.0.1:9011 (unreachable off-node in a host-network job) and no Prometheus job or load-tool target includes :9011, so seq-b replicas are completely unmonitored — which is exactly what makes the F02.1 zombie invisible in production. The spec's Observability section ("the seq-b twins on :9011 are additional, not double-counted") describes neither actual outcome.
- **Still present at HEAD**: yes
- **Suggested fix**: Add a `replica` (group) label to the sequencer metrics or stamp it via `host_id`, bind both listeners on 0.0.0.0 (or the node IP), add :9011 scrape targets, and change dashboard aggregations to `max by (partition)` for stream-derived totals (or filter one replica group) so per-shard semantics survive replication.

### F02.5 [low] [logic] — `sequencer-replica-kill` chaos case doesn't pin its load to the killed replica's shard, so ~half of runs assert nothing about the failover
- **Where**: deploy/cluster/scripts/chaos.sh:418-433 (one fresh funded account per case, sender → shard by address hash), 449-456 (kills shard 0's replica A specifically); at HEAD same lines.
- **What**: The case hard-kills seq-a on node-0 (shard 0's replica A), but the case's single load sender lands on shard 0 or shard 1 depending on `partition_for(address)` of whichever funded account index the case happens to draw. When it hashes to shard 1, the tx-delivery verdict exercises an untouched shard, and `assert_progress` passes on sealer boundaries that tick ~4/s even with zero tx flow — the "no stall" guarantee is then untested for the shard that lost a replica. Similarly, `hard-sequencer`'s `inject_hard ... sequencer` filter (`docker ps --filter name=sequencer -q | head -1`) now matches both `sequencer-a` and `sequencer-b` tasks and kills an arbitrary one.
- **Still present at HEAD**: yes
- **Suggested fix**: Pick the case's funded account so that `partition_for(sender) == 0` (precompute the account→shard map, or iterate account indices until the shard matches), and tighten the `hard-sequencer` filter to `sequencer-a`/`sequencer-b` explicitly.

### F02.6 [low] [logic] — Racing replicas double every `DuplicatedTx` rejection, and divergent floors can produce a rejection racing a success for the same tx
- **Where**: crates/sequencer/src/sequencer.rs:324-333 (`ReportDuplicate` → `publish_error`), src/state.rs:70-79 (Past path); tx_errors publisher has no dedup key beyond `{sender, nonce}` (kardamom-sequencer.rs:319-341). Same at HEAD.
- **What**: The cluster dedups refs, but nothing dedups `tx_errors`: every past-nonce tx now yields two `TxError{DuplicatedTx}` publications (one per replica). Worse, after a restart the twins' nonce floors can diverge (one stream-derived, one hydrated), so for a retransmitted tx one replica emits a rejection while the other publishes the (deduped) ref — ingress may release a parked client with a "duplicate" receipt for a tx that in fact confirmed. Floors can only lag (never lead) the true next nonce, so a *fresh* valid tx cannot be spuriously rejected; impact is duplicate/contradictory client signals, not lost txs.
- **Still present at HEAD**: yes
- **Suggested fix**: Dedup tx_errors at ingress by `{sender, nonce, reason}` (it already dedups receipt copies by tx hash), and treat a later success signal as overriding an earlier duplicate-rejection for the same correlation.

### F02.7 [nit] [quality] — `keep_sequencer_id` override breaks the shard-subscription and determinism invariants it claims to allow
- **Where**: crates/sequencer/src/config.rs:123-128 (`rotate_partition(_, keep_sequencer_id=true)`); crates/sequencer/src/bin/kardamom-sequencer.rs:148 (`let shard_id = cfg.sequencer_id;` — the tx_data subscription key) vs sequencer.rs:253-261 (wrong-shard guard uses `partition_index`). Same at HEAD.
- **What**: An operator combining `--partition-offset` with an explicit `--sequencer-id` (the code path the `rotate_partition_keeps_explicit_sequencer_id` test enshrines, id=7 with partition=1) gets a replica that subscribes to tx_data stream 7 but filters envelopes for partition 1 — it silently drops everything. It also breaks the byte-identical-replica argument (twins would stamp different `TxRef.shard_id` while dedup keys only on `tx_hash`, so the surviving record's shard_id becomes race-dependent).
- **Still present at HEAD**: yes
- **Suggested fix**: Validate `sequencer_id == partition_index` when `partition_offset != 0` (reject the combination), or derive the tx_data subscription from `partition_index` instead of `sequencer_id`.

## Verdict
The core mechanism is sound and well-argued: byte-identical deterministic refs from a shared multicast stream plus first-seen dedup at the ordering authority genuinely gives leaderless no-stall failover, the cross-placement via `meta.node_index` is deterministic and correct (verified rotation math, inventory fallbacks, and port separation), and the new test pins the right three invariants with a mathematically valid order-preservation argument. But the commit's *recovery* story is documentation, not implementation: the deployed binary hydrates nonce floors from an always-empty state DB, so a restarted replica permanently stops covering established senders (F02.1) — the system quietly degrades to P=1 after the first restart while chaos (alloc counts, fresh accounts, boundary ticks) is structurally unable to notice, and seq-b's unmonitored loopback metrics endpoint (F02.4) hides it operationally. The dedup-window safety argument also covers only the restart case, not live laggards (F02.3). Ship-quality deploy and test engineering around a real availability win, undermined by an unimplemented restart-rejoin path that the docs present as done.
