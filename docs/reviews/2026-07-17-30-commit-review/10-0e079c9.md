# 10 0e079c9 — feat: validator nodes (follow + re-execute + MPT state root + BAL cross-check) (#63)

## Summary of change
Adds validator nodes: extracts the role-agnostic execution core into a new `kardamom-engine` crate (behaviour-preserving move from `kardamom-executor`), adds a per-block BAL channel (`tx_bal`, stream 1004) that the executor tees each `BlockDelta` onto, adds a canonical Ethereum MPT state-root computation to `kardamom-state` (storage-incremental, persisted atomically with each block), and introduces the `kardamom-validator` crate/binary that re-executes the canonical stream through the shared engine, cross-checks its write-sets against the executor's BAL and its receipts against `tx_receipts`, and is intended to fail-stop on any proven divergence. The commit also carries a train of cluster-resilience fixes shaken out by the new e2e verdict: self-healing cluster-client sessions with ingress rotation, bounded egress offers in the sealer service, 30s session timeout, boundary-timer re-arm on every leadership term, and chaos-probe fixes.

## Findings

### F10.1 [high] [logic] — Receipt-mismatch "fail-stop" is silently defeated by the commit thread's must-deliver retry loop
- **Where**: crates/validator/src/lib.rs (ValidatorReceiptSink::publish, ~line 322 at HEAD) interacting with crates/engine/src/actor.rs:620 (at HEAD; same code at the commit)
- **What**: The engine's commit thread treats `tx_receipts` publication as must-deliver: `while let Err(e) = c_pub.publish(c_msg.clone()) { … sleep(50ms) }` retries forever on ANY error. For the validator, `ValidatorReceiptSink::publish` returns `Err(ExecutorError::State(..))` on a proven receipt mismatch — but the first (failing) call already `take()`-consumed the published receipt from the buffer, so the retry's second call finds nothing, waits out RECEIPT_WAIT (5s), lands in the `None => Ok(())` "unverified" arm, and the loop exits cleanly. Net effect: on a proven receipt divergence the validator logs, sets the divergence flag/metric, stalls 5s… and then keeps executing and committing blocks indefinitely. The pipeline does not halt and the process does not exit 2 (until an operator signal, at which point `diverged` is finally consulted). Only the write-set (BAL) path actually fail-stops (its error propagates via `sw_queue.submit(..)?` on the exec thread). The CI verdict happens to catch it via `validator_divergence_total`, but the designed process-level fail-stop ("a dead validator alloc IS the divergence signal" — validator.nomad.hcl) does not occur for receipt divergences.
- **Still present at HEAD**: yes
- **Suggested fix**: Make the engine's must-deliver retry distinguish fatal sink errors from transient transport errors (e.g. a `ExecutorError` variant or a `is_fatal()` on the publication trait), or have `ValidatorReceiptSink` remember the mismatch (it already has `divergence`) and keep returning `Err` on retries / have the commit loop check a halt flag. Alternatively have the validator binary watch `Divergence::is_halted()` and initiate shutdown itself.

### F10.2 [high] [logic] — BalBuffer/ReceiptBuffer `take()` restarts the full timeout on every wakeup → wait never times out under a live stream (validator freeze)
- **Where**: crates/validator/src/lib.rs (BalBuffer::take / ReceiptBuffer::take at the commit)
- **What**: `take()` looped `cv.wait_timeout(guard, timeout)` with the **full** timeout re-applied after every wakeup. `insert()` for any other key calls `notify_all`, so under a live chain (a BAL/receipt arriving every ≲5s) a wait for a key that never arrives (one lost BAL frame — the publish is explicitly fire-and-forget/best-effort) never times out: the exec thread hangs forever on one lost BAL while the buffer keeps filling. Observed in production as a total validator freeze with a healthy chain (per the #78 commit message).
- **Still present at HEAD**: no (fixed by 70d0823 — deadline semantics + catch-up skip)
- **Suggested fix**: (already fixed) compute a deadline once and wait on the remaining time.

### F10.3 [medium] [logic] — Cold-start catch-up: ReceiptBuffer has no aged-out skip, so each historical tx blocks the commit thread for the full 5s RECEIPT_WAIT
- **Where**: crates/validator/src/lib.rs:197–215 (ReceiptBuffer::take at HEAD), used by ValidatorReceiptSink::publish (lib.rs:325)
- **What**: A validator starting/restarting behind a running chain re-executes the backlog, but the executor's receipts for historical txs have aged out of the live `tx_receipts` stream and will never arrive. PR #78 (70d0823) added a catch-up skip to `BalBuffer::take` (BACKLOG_LOOKBEHIND vs the buffered head) for exactly this crawl, but `ReceiptBuffer` got only deadline semantics — no skip. So for a tx-bearing backlog the commit thread still waits the full 5s per historical receipt, capping catch-up at ~0.2 tx/s (the exec→commit channel backpressures the whole engine). The #78 lapse test passes because a 30s pause's receipts are still in the term buffer, and an idle-chain cold start has boundary-only blocks (`CMessage::BlockBoundary` returns immediately); a cold start behind a loaded chain would still crawl.
- **Still present at HEAD**: yes
- **Suggested fix**: Mirror the BAL catch-up heuristic in `ReceiptBuffer::take` (skip immediately when the highest buffered `tx_idx` is far ahead of the requested one), or plumb the block-level "aged-out" decision from the writer queue into the receipt sink.

### F10.4 [medium] [quality] — ~200 lines of the validator binary are copy-pasted from the executor binary
- **Where**: crates/validator/src/bin/kardamom-validator.rs (at commit and HEAD) vs crates/executor/src/bin/kardamom-executor.rs (HEAD lines 36–45, 489–, 501–, 546–, 563–, 598–, 607–)
- **What**: `StateDurabilityArg` (+ From impl), `load_genesis`, `build_genesis_alloc`, `LiveTxDataSub`, `LiveTxDepositsSub`, `init_tracing`, `wait_for_shutdown`, and the per-shard tx_data / tx_deposits async→sync bridging blocks (including the replay-merge recovery variant) are duplicated essentially verbatim between the two binaries. The commit's own design note is careful about DRY at the engine layer but leaves the binary wiring duplicated; the two copies have already begun to drift (join_timeout handling, shutdown/select structure).
- **Still present at HEAD**: yes
- **Suggested fix**: Move the shared wiring (subscription bridging, genesis alloc building, durability arg, tracing/shutdown helpers) into `kardamom-engine` (e.g. a `bin_support` module) or a small shared crate, leaving only role-specific seam construction in each binary.

### F10.5 [low] [logic] — Receipt cross-check ignores `logs` (and other published fields): a log-only divergence is undetectable
- **Where**: crates/validator/src/lib.rs:222–226 (`receipt_consistent`, at commit and HEAD)
- **What**: Only `status`, `gas_used`, and `write_set_hash` are compared. `write_set_hash` covers state writes but not event logs, and logs are not derived enrichment (they are execution output carried on the wire and consumed downstream). A divergence that alters emitted log data while leaving state writes/status/gas identical (or a bug in the executor's log plumbing) passes the cross-check silently — a false-negative window in the "validator verifies the executor" story. Same for `contract_address` / `effective_gas_price` / `cumulative_gas_used`, which are cheaper to derive but are still published fields consumers act on.
- **Still present at HEAD**: yes
- **Suggested fix**: Include `logs` (or a hash of them) in `receipt_consistent`; document explicitly which published fields are deliberately out of scope.

### F10.6 [low] [logic] — Verification buffers are unbounded; late arrivals leak permanently
- **Where**: crates/validator/src/lib.rs:109–123, 180–195 (BalBuffer/ReceiptBuffer, at commit and HEAD)
- **What**: `insert()` has no size cap and no eviction of entries below the consumer's cursor. During a long catch-up the buffers accumulate the entire live stream (hours of `BlockDelta`s in RAM); and any artifact that arrives just after its `take()` gave up (the 5s race) is inserted and never removed — a slow permanent leak keyed by block/tx_idx that the cursor has already passed.
- **Still present at HEAD**: yes
- **Suggested fix**: Track the last-taken key and drop inserts at/below it; optionally cap the map size (evicting the oldest entries and counting them as missing).

### F10.7 [low] [quality] — Dead code: `BalPublisher` and `Subscribers::bal()` are never used

The `BalPublisher` struct and `Subscribers::bal()` convenience added in this commit have no callers anywhere in the workspace.
- **Still present at HEAD**: yes

### F10.9 [nit] [quality] — Stale/contradictory comments: "co-resident executor", "executor-class node", "single publisher", and a state-root gauge that mirrors the block gauge
- **Where**: deploy/cluster/nomad/validator.nomad.hcl:15 vs :75; deploy/cluster/scripts/ci-cluster.sh:570; crates/log/src/config.rs:190; crates/validator/src/metrics.rs:54–56 (all at HEAD too)
- **What**: (a) The nomad job header says the validator runs on the aux node with "no executor co-resident", but the `--cluster-egress-endpoint` arg comment still justifies port 40230 by "the co-resident executor's session already binds" — a leftover from the pre-fix placement; ci-cluster.sh's verdict comment likewise still says "one alloc on an executor-class node". - **Still present at HEAD**: yes

### F10.10 [low] [logic] — Sealer egress: bounded offer retry (8 spins, no idle) silently drops canonical frames per session
- **Where**: cluster/sealer-service/service/src/main/java/io/kardamom/sealer/cluster/SealerClusteredService.java (offerToSession, at the commit)
- **What**: The fix for the unbounded single-thread retry loop replaced it with `MAX_OFFER_RETRIES = 8` immediate re-offers — no idle between attempts, so under ordinary transient back-pressure the 8 tries burn in microseconds and the frame is dropped for that session, silently (no log, no counter). A gap in the canonical tx_ordering egress surfaces to the client only later as a confusing `BoundaryMisaligned`/join failure. (The trade-off itself — not stalling the whole cluster on one wedged client — is right; the mechanism was too eager and unobservable.)
- **Still present at HEAD**: no (fixed by 52a32a2 — time-based `OFFER_DEADLINE_NS` and `session.close()` instead of dropping frames: "a closed session is a fact the client sees; a gap is silent corruption")
- **Suggested fix**: (already fixed at HEAD).

## Verdict
A large but well-structured commit: the engine extraction is genuinely behaviour-preserving (re-exports keep every existing path compiling), the MPT trie code is clean, pure, well-normalized (EIP-161, zero-sentinel mapping) and tested against an independent model rebuild, and the "missing artifact ⇒ unverified, never false-positive" discipline in the cross-check design is correct and consistently applied. The cluster-resilience fixes bundled in (session self-heal with ingress rotation, boundary-timer re-arm per leadership term, MAX-across-replicas probe) are each well-evidenced root-cause fixes. The serious problems are in the fail-stop story: the receipt-divergence path never actually halts anything because the engine's must-deliver retry swallows the sink error (F10.1, still live), the original `take()` timeout-reset bug could freeze the validator outright (F10.2, since fixed), and the catch-up fix in #78 covered only the BAL half of the wait problem (F10.3). The binary-level duplication with the executor (F10.4) is the main structural debt. Cross-check comparison semantics (write-set equality on sorted-order vecs; receipt core-field triple) are sound for true-positive detection, with a documented-but-real false-negative window for logs (F10.5).
