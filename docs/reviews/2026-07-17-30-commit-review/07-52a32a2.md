# 07 52a32a2 — feat(cluster): canonical-stream replay (F3) + member/session/storage resilience fixes (#72)

## Summary of change
Adds the F3 canonical-stream replay protocol closing the gap left by the cluster-only migration (#67): the Java `SealerClusteredService` retains up to 65536 framed egress frames (records + boundaries, emission order) and serves `KIND_REPLAY_REQUEST(from_index, from_block)` by re-offering retained frames >= the cursor to the requesting session, ending with `REPLAY_DONE` or an honest `REPLAY_UNAVAILABLE` carrying the retention floor. The Rust client sends `REPLAY_FROM(cursor)` on every session establishment (resent every 3s until the delivery cursor advances), and `ClusterTxOrderingSubscription` totally orders replayed + live frames by their keys (records by index, boundaries by block_number/end_tx_idx), deduping below the cursor. Also bundles: in-process launch retry past the stale mark-file liveness window, a container-side termination hook, zombie-session close on egress `NOT_CONNECTED` (deadline-then-close), 8MB log terms + 1MB client control terms + 2G aeron tmpfs, deadline (not per-wakeup) semantics in `BalBuffer`/`ReceiptBuffer::take`, validator bounded join wait + Nomad restart-based recovery, and a strict-again chaos verdict.

Replay-correctness assessment vs. the commit's claims: the core gap/duplicate machinery is sound — the cursor atomics are only ever read as conservative floors (a torn read can only add duplicates, never gaps), BTreeMap-keyed buffering makes replay/live overlap duplicates harmless, and delivery is strictly cursor-driven so records can never be delivered out of index order. What the commit does NOT deliver is its snapshot-restart claim (F07.1), and boundary/record *interleaving* order has a real hole (F07.2). Project memory's "known F3 follow-ups" (multicast side-stream refetch, resend via retrying publish, replay observability) are acknowledged in-commit or fixed later; F07.1/F07.2 are neither.

## Findings

### F07.1 [high] [logic] — Snapshot-restored member serves a bogus REPLAY_DONE for pre-snapshot ranges: silent gap instead of the claimed UNAVAILABLE
- **Where**: `cluster/sealer-service/service/src/main/java/io/kardamom/sealer/cluster/SealerClusteredService.java:112-113` (floor init), `:135-147` (`onStart`), `:302-303` (floor check) — same lines at the commit and at HEAD.
- **What**: The commit message and the in-code comment (line 105-106) claim "a member restarted from snapshot serves REPLAY_UNAVAILABLE for pre-restart ranges, an honest degradation." The code does not do this. `onStart` restores `state` from the snapshot image but leaves `retained` empty and `firstRetainedIndex = 0` / `firstRetainedBlock = GENESIS`. A replay request with a cursor anywhere in `[0, snapshotPoint)` passes the availability check (`fromIndex < 0` is never true), iterates a `retained` deque that only holds post-restart frames, and ends with `REPLAY_DONE`. The client then clears `catching_up`, waits forever for a record at `next_index` that will never arrive, keeps buffering live frames, and re-sends the request every 3s — each resend getting the same bogus DONE — until it either hangs indefinitely or, hours later under load, dies on the misleading `MAX_PENDING` "catch-up buffer overflow" error. The exact failure class replay was built to eliminate (silent canonical gap) comes back on the first leader that was restored from a snapshot. Triggering requires a snapshot to exist (`onTakeSnapshot` is implemented; snapshots are taken via SNAPSHOT admin action, not automatically), which is why the chaos suite's kill -9-heavy runs did not surface it.
- **Still present at HEAD**: yes
- **Suggested fix**: In `onStart`, when `snapshotImage != null`, initialize the floors from the restored state: `firstRetainedIndex = state.canonicalCount(); firstRetainedBlock = state.blockNumber() + 1;`. That makes the documented "honest UNAVAILABLE" true. (Longer term: snapshot the retention or the floors.)

### F07.2 [medium] [logic] — Boundary-only gap across a reconnect is not detected: replayed boundary delivered after a record it canonically precedes
- **Where**: `crates/engine/src/reader/cluster.rs:103-105` (live-mode delivery rule) and `:115-150` (`ingest` gap detection) — same at the commit and at HEAD (file unchanged since 52a32a2).
- **What**: `catching_up` is entered only when a *key gap* is observed (`index > ni` or `block_number > nb`). Record indices are contiguous, so a missed record is always detected — but boundary continuity cannot be inferred from record continuity. Failure scenario: boundary `nb` (with `end_tx_idx == ni`) is emitted during a brief session outage; the client reconnects and the first live frame is record `ni` exactly (next expected index — no gap observed). `try_deliver` is in live mode with no boundary buffered at `nb`, so it delivers record `ni` and advances the cursor. The replayed boundary `nb` then arrives (the REPLAY_FROM sent on connect covers it), satisfies `end_tx_idx <= ni+1`, and is delivered *after* record `ni` — but canonically block `nb` seals before record `ni` (which belongs to block `nb+1`). Downstream applies messages in delivered order, so the replica seals block `nb` with one extra record: a canonical-order divergence between replicas, silent until the validator's BAL cross-check trips. The window is narrow (outage must miss only boundaries and reconnect must land a next-index record before the next live boundary, i.e. within one ~250ms-2s tick) but chaos-grade session churn hits narrow windows.
- **Still present at HEAD**: yes
- **Suggested fix**: Enter catch-up mode on every session (re)establishment — e.g. a shared flag set by the session thread alongside the REPLAY_FROM send, cleared only on `ReplayDone` — instead of only on an observed key gap. In catch-up mode the existing rule already refuses to deliver a record until the boundary at `next_block` proves it precedes it.

### F07.3 [medium] [logic] — Replay is served synchronously on the deterministic cluster service thread with a 1s-per-frame offer deadline
- **Where**: `SealerClusteredService.java:302-322` (`handleReplayRequest` loop) and `:438-450` (`offerBytesToSession`) at HEAD; same structure at the commit.
- **What**: `handleReplayRequest` re-offers up to `retentionCap` (default 65536) frames in a tight loop on the single cluster service thread, and each back-pressured offer may spin up to `OFFER_DEADLINE_NS` (1s). A slow consumer replaying a large window through the (now 1MB-term) egress publication will be back-pressured for most of it; worst case the leader's service thread stalls for minutes-to-hours, during which *every* session's egress and all log-message processing behind it freeze — the same "pipeline frozen while Raft looks healthy" symptom this PR spent several sub-commits chasing. (On followers `ClientSession.offer` is mocked to succeed, so only the leader stalls; after a deadline expiry the session is closed and remaining offers return CLOSED quickly, bounding a single pathological session — but a merely-slow session never trips the deadline and stalls the loop frame by frame.)
- **Still present at HEAD**: yes
- **Suggested fix**: Serve replay incrementally — chunk the retained range and continue from `doBackgroundWork`/a cluster timer, or track a per-session replay cursor and drain it as the publication frees space, with a total time budget per request.

### F07.4 [low] [security] — 2.5MB build artifact committed: deploy/cluster/docker/kardamom-cluster-node.jar
- **Where**: `deploy/cluster/docker/kardamom-cluster-node.jar` at the commit (Bin 0 -> 2502100 bytes); absent at HEAD.
- **What**: A compiled cluster-node jar (a docker build staging artifact) was committed. Committed binaries are unauditable, bloat history permanently (the blob remains in git history even after removal), and risk drift between reviewed source and deployed bytes.
- **Still present at HEAD**: no (fixed by 3e6de2a, which drops the jar and gitignores the staging path)
- **Suggested fix**: Already removed and gitignored; consider a history rewrite only if repo size becomes a problem.

### F07.5 [low] [logic] — MAX_POSITION_EXCEEDED offer result returns without closing the session: residual zombie path
- **Where**: `SealerClusteredService.java:438-465` (`offerBytesToSession` / `offerToSession`) and `:468-482` (`retryable`) at HEAD; same at the commit.
- **What**: The commit's own rationale for the NOT_CONNECTED change is that a session the service silently stops offering to is "a ZOMBIE the client cannot detect." But a non-retryable `MAX_POSITION_EXCEEDED` still takes the `return`-without-close path in both offer helpers: the publication is permanently dead (position limit), every subsequent frame for that session is silently dropped, and the session stays alive on ingress keep-alives — the identical zombie, via a rarer trigger (bounded 1MB terms make max-position effectively unreachable in practice, hence low).
- **Still present at HEAD**: yes
- **Suggested fix**: In both offer helpers, close the session on any terminal result other than `CLOSED` (which means it is already closed), rather than returning silently.

### F07.6 [nit] [quality] — ci-cluster.sh divergence grep reads only the first alloc of the validator job
- **Where**: `deploy/cluster/scripts/ci-cluster.sh:677-679` at HEAD (added by this commit at ~653-660).
- **What**: `nomad job allocs -t "{{range .}}{{.ID}} {{end}}"` prints all alloc IDs on one line; `awk '{print $1}'` keeps only the first. In-place restarts share an alloc (the common case this grep targets), but a *rescheduled* validator gets a new alloc and a pre-reschedule "halted on divergence" line in the old alloc's log would be missed — precisely the "quietly absorbed diverged validator" the comment says must not happen.
- **Still present at HEAD**: yes
- **Suggested fix**: Loop the grep over all alloc IDs returned by the template.

## Verdict
A dense, well-forensicated commit: the replay protocol's core ordering/dedup design is genuinely sound (conservative atomic cursor floors, key-driven total ordering, honest UNAVAILABLE-on-eviction), the bundled fixes (mark-file launch retry, zombie-session close, term-length/tmpfs sizing, condvar deadline semantics) each come with a credible root-cause narrative, and test coverage (5 ordering unit tests + 2 in-JVM TestCluster integration tests) exercises the main paths. But the commit over-claims in two places that matter for its own headline guarantee of a gapless canonical stream: the "honest degradation" after snapshot restart is not implemented (F07.1 — a silent-gap DONE, the exact failure replay exists to prevent), and gap detection cannot see a boundary-only gap across a reconnect (F07.2 — a narrow but real canonical-order inversion). Both are still present at HEAD and are the actionable residue of an otherwise strong change; F07.3's synchronous replay on the service thread is a self-inflicted instance of the freeze pattern the PR was fixing elsewhere.
