# 14 b00b3e0 — refactor: remove kardamom-node, converge on the cluster implementation (#57)

## Summary of change
Deletes the monolithic in-memory `kardamom-node` crate (`crates/node`) and its `kardamom` binary crate (`crates/kardamom`), converging the repo on the Aeron-based cluster. Consumers are repointed: bench and deployer now import `Genesis`/`AllocEntry` from `kardamom-types`; the deployer dev-genesis test asserts on the parsed alloc directly; the in-process bench `Harness` is rewritten to drive a real `IngressProxy` over `MockChannels` plus a fake-executor receipt reflector; observability artifacts (kardamom-node dashboard, Prometheus job, obs-test entry, docs, README) are cleaned up and the overview block-height panel is repointed to the sealer/executor gauges.

## Findings

Removal completeness was checked at HEAD: no load-bearing references to the deleted crates remain. `Cargo.toml` uses a `crates/*` member glob; `deploy/prometheus.yml`, `crates/obs/tests/dashboards.rs`, and the overview dashboard were all updated in-commit (the repointed panel queries `kardamom_sealer_block_number` / `kardamom_executor_block_number`, which exist — see `crates/bench/src/load/scrape.rs`). Remaining `kardamom_node` / `crates/node` hits at HEAD are unrelated (the Ansible inventory `kardamom_node=` host var, the `kardamom-node:ci` DinD image tag in `deploy/cluster/scripts/ci-cluster.sh:32`) or historical comments/plan docs.

### F14.1 [low] [quality] — `kardamom-bench-harness` still advertises the removed node and its `calls`/`mixed` subcommands cannot work against the ingress stand-in
- **Where**: `crates/bench/src/bin/harness.rs:21,29,63-80` (at the commit and unchanged at HEAD)
- **What**: The commit repointed `Harness` at an in-process `IngressProxy` but did not touch the harness binary. Its `about` text still says "Run the bench against an in-process kardamom node", and it still exposes `calls` and `mixed` workloads. The ingress JSON-RPC surface has no `eth_call` (`crates/ingress/src/json_rpc.rs` serves only the write path; even `eth_getBalance`/`eth_getTransactionCount` are stubbed "deferred"), so `kardamom-bench-harness calls|mixed` now fails at runtime in `CallsWorkflow::prepare` (method not found). The sibling smoke test (`crates/bench/tests/smoke.rs`) explicitly switched to `TransfersWorkflow` for exactly this reason, but the binary was left offering the broken workloads.
- **Still present at HEAD**: yes
- **Suggested fix**: Restrict the harness binary to `transfers` (or gate `calls`/`mixed` behind a clear error) and update the `about`/doc text to say "in-process ingress stand-in".

### F14.2 [nit] [quality] — `BenchWorkflow::genesis_alloc` is no longer called on any runtime path; stale doc comment claims it is validated
- **Where**: `crates/bench/src/harness.rs:82` and `crates/bench/src/workflow.rs:46` (at the commit and at HEAD)
- **What**: The old `build_node_and_client` built and validated a `Genesis` from `workflow.genesis_alloc(...)`; the new `build_ingress_and_client` ignores genesis entirely (the ingress stand-in starts with an empty `InMemoryStateDb` and the fake executor receipts everything). `Harness::run`'s doc still says it "Errors if the genesis derived from `workflow.genesis_alloc` is invalid", which is now false, and the trait method is dead weight for the in-process path (only meaningful as documentation for external chains).
- **Still present at HEAD**: yes
- **Suggested fix**: Fix the doc comment; either drop `genesis_alloc` from the trait or document that it now only describes the funding the workflow expects from an external chain.

## Verdict
A clean, well-executed removal. The commit checked all the consumer surfaces that matter — workspace membership, imports, tests, Prometheus job, dashboards, docs, README — and the bench/deployer rewrites are sensible replacements (the deployer test still covers its stated regression target; the ingress stand-in exercises the real proxy hot path without Aeron). The fake-executor reflector correctly keys receipts on `(sender, nonce)` by decoding the raw tx the same way the proxy does. The only misses are peripheral drift in the untouched `kardamom-bench-harness` binary: stale "node" wording and two subcommands (`calls`, `mixed`) that can no longer succeed against the write-only ingress stand-in.
