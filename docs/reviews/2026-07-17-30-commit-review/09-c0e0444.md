# 09 c0e0444 — feat(state): branch-node-incremental state trie (validator) (#70)

## Summary of change
Replaces the per-block full-rebuild MPT state root (from #63) with a reth-style node-incremental trie: four new mdbx tables (stored `BranchNodeCompact` nodes for the account/storage tries + a hashed-state mirror, schema v2), a `PrefixSet`-driven recursive walker over `alloy_trie::HashBuilder` that skips unchanged stored subtries by hash, and `TrieMode::{Off,Incremental,ShadowCheck}` in the `StateWriter` (root advances atomically with the block txn; `seed_genesis` builds the genesis mirror/root). The validator binary gains `--trie-shadow-check N` (full-rebuild cross-check, fail-stop on mismatch) and now exits when its engine loop halts. The commit also carries a series of hard-won Aeron cluster fixes (egress close-on-backpressure instead of frame drops, 90s session timeout, boundary-timer re-arm per term, Nomad `restart mode=delay` for Raft members) and deploy/CI updates.

Differential testing exists and is layered: a 50-block randomized incremental-vs-full-rebuild equivalence test, a 3-block writer model/persistence test on the incremental path, a genesis-root test, and the cluster e2e running `--trie-shadow-check 8` asserting `shadow_checks>0 && mismatch==0`. Node hashing/RLP is delegated to alloy-trie (storage leaf = RLP(U256), account leaf = RLP(TrieAccount); `ZERO→KECCAK_EMPTY/EMPTY_ROOT_HASH` sentinel canonicalization and EIP-161 exclusion are correct and unit-tested; `hash_for_nibble` indexing and `storage_root_unsorted`/`state_root_unsorted` pre-hashed-key usage verified against alloy-trie 0.9.5 source). Branch collapse itself is handled by `HashBuilder` (walker replays surviving children; single-child collapse to extension/leaf is HashBuilder's job).

## Findings

### F09.1 [high] [logic] — Walker deletion tracking misses stored nodes under extensions: stale orphans can later be read and silently diverge the root
- **Where**: `crates/state/src/trie/walker.rs:204-216` (`finalize`: `removals = visited − updated`), `walker.rs:70`/`walker.rs:157` (the `None` full-leaf-rebuild fallback that never visits deeper stored nodes); same lines at HEAD (trie code unchanged since this commit).
- **What**: Removals are computed only from nodes the walker *exactly visited*. But alloy-trie/reth `tree_mask` semantics mean "the child *subtree* contains stored nodes", not "a node is stored at exactly `parent+nibble`" — under an extension, the stored node lives at a deeper path. When the walker recurses to `parent+[i]` and the exact-path `get_branch_node` misses (node stored deeper, e.g. at `[3,5]` under root child 3), it correctly rebuilds that subtrie from leaves — but if the change collapsed the deeper stored node (e.g. `[3,5]` loses its branch child), that node is never visited, never removed, and becomes a **stale orphan**. Failure scenario: later blocks regrow the subtree so a fresh node at `[3]` carries `tree_mask` bit 5 via extension propagation (`update_masks` sets the bit whenever *any* descendant under `[3,5,…]` is retained, without necessarily re-upserting at `[3,5]`); the next walk with a change under `[3,5]` then exact-gets the **stale** node at `[3,5]` and skips its "unchanged" children via **stale hashes** (`add_branch(node.hash_for_nibble(i), true)`) → wrong root, silently. Secondary effect: orphan rows accumulate unboundedly in `account_trie`/`storage_trie` (slow disk growth) even when never re-read. reth avoids this class with range-seek trie cursors and range-based deletion collection. The 50-block randomized test cannot reach this: 40 accounts / 8 slots essentially never produce a *retained* branch node under an extension (needs ≥3-4 keys sharing ≥2 nibbles plus a sub-branch), let alone the collapse-then-regrow sequence.
- **Still present at HEAD**: yes. Mitigated only when `ShadowCheck` is on: the hashed mirror is always correct, so a divergence becomes a fail-stop within `every_n` blocks (deploy uses 8). The binary's **default** (`--trie-shadow-check` absent) is `TrieMode::Incremental` — no cross-check, and the sequencer publishes no root to compare against, so divergence would be fully silent.
- **Suggested fix**: When the exact-path lookup misses and a subtrie is rebuilt from leaves, range-delete every stored node under that nibble-path prefix in the same txn (a `del_prefix` over the node-key space, before applying upserts); alternatively adopt reth-style range-seek cursors so stored nodes under extensions are found, visited, and swept. Consider defaulting the validator to a nonzero shadow-check cadence until then.

### F09.2 [medium] [logic] — Egress offer on a NOT_CONNECTED session still silently drops the frame (the exact corruption the commit set out to eliminate)
- **Where**: `SealerClusteredService.java` at the commit: `offerToSession` returns immediately when `!retryable(result)`, and `retryable` treats only `BACK_PRESSURED`/`ADMIN_ACTION` as retryable — `NOT_CONNECTED` is terminal, so the frame is dropped with **no** `session.close()`. HEAD: `SealerClusteredService.java:451-484`.
- **What**: The commit's own message establishes that a silently missed boundary frame makes a client seal two blocks as one and provably diverge (observed `validator_divergence_total = 1`). The fix closes sessions on back-pressure exhaustion, but a session whose egress publication is transiently unconnected (session open, leader failover re-creating egress) takes the silent-drop path while its ingress keep-alives keep the session alive — a zombie the client cannot detect. This was in fact later observed ("a validator starved for 30+ minutes on an intact session after a leader kill", per the HEAD comment).
- **Still present at HEAD**: no (fixed by 52a32a2, which makes `NOT_CONNECTED` retryable-within-deadline and closes on exhaustion). `MAX_POSITION_EXCEEDED` still returns without close at HEAD — pathological and arguably fine, but it is another no-signal drop.
- **Suggested fix**: n/a at HEAD; done.

### F09.3 [low] [logic] — `update_for_block` swallows all mdbx errors on mirror deletes, not just NotFound
- **Where**: `crates/state/src/trie/mod.rs:189` (zero-valued slot delete from `hashed_storage`) and `mod.rs:235` (empty-account delete from `hashed_accounts`); same at HEAD.
- **What**: `let _ = txn.del(...)` discards every error. A genuine mdbx failure (map-full, bad txn) would leave the mirror containing a slot/account that should be gone while the block txn may still commit — the root then diverges from the reference with no error surfaced. Sibling code (`del_prefix`, `apply_trie_updates`) correctly matches `MdbxError::NotFound` and propagates the rest.
- **Still present at HEAD**: yes.
- **Suggested fix**: Match on `NotFound` and propagate other errors, as `del_prefix` already does.

### F09.4 [low] [quality] — Equivalence test drives a reimplementation of the production update path, over a pool too small for the risky trie shapes
- **Where**: `crates/state/src/trie/incremental_tests.rs:41-131` (`apply_block` + a duplicated `del_prefix`); same at HEAD.
- **What**: The randomized 50-block gate exercises a test-local copy of the mirror-maintenance/delete logic rather than `trie::update_for_block` itself (which is only covered by the 3-block writer test and the e2e shadow-check), so the two can drift; and the 40-account/8-slot pool produces a shallow trie whose stored nodes sit at exact child paths — the extension/collapse/regrow geometry of F09.1 is effectively unreachable. The spec itself names "walker deletion/collapse" the dominant risk, yet the gate can't generate the shapes that stress it.
- **Still present at HEAD**: yes.
- **Suggested fix**: Drive the randomized blocks through `update_for_block` (build `BlockDelta`s), grow the pool (hundreds of keys) and/or add a targeted regression that constructs a stored-branch-under-extension, collapses it, regrows it, and asserts against the oracle; assert the node tables contain no orphans after each block.

### F09.5 [low] [quality] — Incrementality degrades to subtree rebuilds more than the docs claim
- **Where**: `crates/state/src/trie/walker.rs:92-104` (tm-set/hm-clear children are always recursed, even when unchanged, because extension children have their parent hash bit cleared by HashBuilder), `walker.rs:70` (exact-get miss ⇒ full leaf rebuild of the subtrie); module doc `trie/mod.rs:9` claims "~O(changed keys)"; same at HEAD.
- **What**: Any visited node's extension-shaped children are fully re-walked and their identical branch nodes re-upserted every time the parent is touched; sparse fringes (and any trie whose top-level node is an extension, where `get_branch_node("")` misses) pay repeated full-subtree rebuild and write amplification. Correctness is unaffected — the cost claim in the docs is optimistic for small/sparse tries.
- **Still present at HEAD**: yes.
- **Suggested fix**: Note the limitation in the module docs, or skip unchanged extension children by materializing their subtree hash (e.g. store the extension head's hash in the parent as reth does via range-seek positioning).

### F09.6 [nit] [quality] — Comment/docs drift and small duplication
- **Where**: `crates/state/src/schema.rs:33` ("len-prefixed packed nibbles" — keys are actually raw *unpacked* nibbles, one per byte, per `trie/cursor.rs`); `deploy/cluster/scripts/ci-cluster.sh:683` (comment claims `--trie-shadow-check 1` while `validator.nomad.hcl` deploys `8` — changed in this same commit); node-key construction triplicated (`cursor.rs::node_key`, the `key` closure in `mod.rs::apply_trie_updates`, inline in `update_for_block`). All still present at HEAD.
- **What/Suggested fix**: Align the comments; share `node_key`.

## Verdict
A large, carefully engineered commit whose core algorithm is sound for the common dense-trie case and is unusually well instrumented against its own failure modes: the shadow-check oracle is a genuinely independent code path, the randomized differential test is real, and the writer keeps root+state atomic in one txn. RLP/hashing, sentinel canonicalization, EIP-161 exclusion, and HashBuilder ordering/collapse handling all check out against alloy-trie 0.9.5. The serious gap is the visited-minus-updated deletion scheme (F09.1): it is unsound under extension geometry, can leak orphan nodes forever, and in a rare but constructible collapse-then-regrow sequence can feed stale hashes into the builder — silent root divergence in the default `Incremental` mode, since only the opt-in shadow check would catch it. The test gate cannot reach that geometry, so "50 blocks equivalent" overstates the proof. The accompanying cluster fixes are strong root-cause work (the back-pressure frame-drop bug it caught and fixed mid-PR is exactly the right instinct), though the same silent-drop reasoning missed `NOT_CONNECTED` until #72. Ship-worthy given the shadow-check deploy cadence of 8, but F09.1 should be fixed before Incremental-without-shadow-check is trusted.
