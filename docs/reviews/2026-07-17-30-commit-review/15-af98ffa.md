# 15 af98ffa — test(cluster): sustained-load + chaos resilience suite (#56)

## Summary of change
Adds `kardamom-load` (a new `crates/bench/src/load/` module + binary): an open-loop ramp→soak load harness that pre-generates per-sender nonce-ordered tx queues, paces submits through ingress, tracks each tx by locally-computed hash, scrapes cluster Prometheus metrics via `docker exec`, and evaluates a pass/fail verdict (completeness, drop accounting, per-executor keep-pace). Adds `deploy/cluster/scripts/chaos.sh` (kill ingress/sequencer/executor/sealer/whole-node under steady load, assert Nomad recovery within SLOs + pipeline progress + load verdict), Nomad restart/reschedule/update stanzas, and shards the suite across five CI runners in `cluster-e2e.yml`. The known-broken `sealer-hard` case is excluded from the CI shards (issue #58).

## Findings

Context: the memory of the July 2026 cluster-e2e flakiness campaign confirms this suite flaked heavily in practice and needed several follow-up PRs (#63, #72, #74) — some of the risks below are exactly what those PRs later fixed, others are still live.

### F15.1 [medium] [logic] — the headline "must-deliver" gate is structurally vacuous: `missing` can never be non-zero
- **Where**: `crates/bench/src/load/engine.rs:133-149,210-245` and `crates/bench/src/load/accounting.rs:176-181` (same lines at HEAD — both files unchanged since this commit)
- **What**: `Pending { accepted: true }` is never constructed anywhere: an accepted submit calls `tracker.confirm(...)` immediately (on-offer ⇒ receipt already arrived) and never enters `pending`; only failed submits enter `pending`, always with `accepted: false`. Therefore `Tracker::remaining_pending()` always returns `missing == 0`, and the `assert_all_delivered` failure "accepted tx(s) never receipted (must-deliver violated)" can never fire. Delivery of accepted txs is *assumed* from the ingress on-offer RPC contract rather than independently verified — if ingress ever acked before the receipt actually landed (the exact bug class a resilience suite should catch), the suite would still pass. The best-effort re-fetch even defaults to success (`receipt_status(...).unwrap_or(1)`), so a lost receipt also can't surface as `bad_status`.
- **Still present at HEAD**: yes
- **Suggested fix**: Keep counting accepted-as-delivered for chaos framing, but make the gate real: in non-chaos soak mode, treat a failed post-accept `eth_getTransactionReceipt` re-fetch as `missing` (the ingress cache is only volatile across restarts, which don't happen in soak); or delete the dead `missing` plumbing and document that must-deliver rides on the on-offer contract.

### F15.2 [medium] [logic] — indiscriminate submit retry + hard `seq_dropped > 0` gate: duplicate resubmission can fail chaos runs
- **Where**: `crates/bench/src/load/engine.rs:196-207` (retry loop), `crates/bench/src/load/accounting.rs:185-190` (hard gate, applied even in `chaos_mode`); same at HEAD
- **What**: `submit_task` retries on *any* submit error with no error-kind discrimination. During ingress chaos, a submit whose HTTP connection dies after the tx was already forwarded (or a parked on-offer call cut off by the ingress kill) is retried; the ingress dedup/receipt caches are in-memory and volatile across the restart (per this commit's own message), so the duplicate reaches the sequencer, is counted by `kardamom_sequencer_tx_dropped_past_total`, and `evaluate` turns any positive `seq_dropped` delta into a hard failure — even in chaos mode. A tx that was in fact delivered exactly once on-chain can thus flip the `graceful-ingress`/`hard-ingress` shard to FAIL.
- **Still present at HEAD**: yes
- **Suggested fix**: Either tolerate a bounded `seq_dropped` delta in chaos mode (it is expected retransmission noise), or before retrying check `eth_getTransactionReceipt` for the locally-known hash and skip the resubmit if it landed.

### F15.3 [medium] [logic] — `assert_count` recovery SLO can pass vacuously before the kill takes effect
- **Where**: `deploy/cluster/scripts/chaos.sh:127-134` at the commit; same helper at `deploy/cluster/scripts/chaos.sh:281-288` at HEAD
- **What**: `assert_count <job> <N>` polls `until count_running >= N`. Immediately after `nomad alloc stop` (or a hard `docker kill` of the inner task) the doomed alloc can still report `ClientStatus == running` on the first poll, so the assertion can succeed instantly against the *old* alloc — i.e. "recovered within SLO" is asserted without ever observing the outage, let alone the recovery. This is most acute for `graceful-executor` (stop 1 of 3, count still reads 3) and the count-1 singleton cases (`ingress`, `sealer`). Actual recovery is then only covered indirectly by `assert_progress` (a single 10s boundary-counter window) and the load verdict.
- **Still present at HEAD**: yes
- **Suggested fix**: Record the killed alloc ID and require a *different* running alloc ID (or first wait for the count to dip below N, then return to N) before starting the SLO clock.

### F15.4 [medium] [logic] — verdict race: spawned submit tasks are never joined; `drain` can exit before in-flight submits resolve
- **Where**: `crates/bench/src/load/engine.rs:247-291` (pacer spawns detached tasks), `engine.rs:293-320` (`drain` breaks as soon as `pending` is empty), `crates/bench/src/load/mod.rs:283-289` (drain → 3s sleep → final counts); same at HEAD
- **What**: `pacer` fire-and-forgets each `submit_task`; nothing joins them. After the send window, up to `max_in_flight` (default 256) tasks can still be parked inside a 30s `REQUEST_TIMEOUT` `eth_sendRawTransaction` (typical during a chaos outage). `drain` snapshots `pending` — which only ever contains *already-failed* submits — and breaks immediately when it is empty, so after only a 3s settle the final `counts()`/`remaining_pending()` read can misclassify still-in-flight txs: they are counted `offered` but appear as neither `accepted`, `missing`, nor `unlanded`. In `Offered` mode this *under*-counts real failures (gate silently too lenient); pending entries inserted after `drain` returned are never re-polled at all, and drain-confirmed latencies are inflated by the 1s poll granularity.
- **Still present at HEAD**: yes
- **Suggested fix**: Collect the spawned tasks in a `JoinSet` and await them (bounded by `drain_timeout`) before draining/evaluating; have `drain` loop until both `pending` is empty *and* no submit tasks remain (or the deadline passes).

### F15.5 [low] [logic] — keep-pace FROZEN check false-positives on a restarted executor whose block gauge reset
- **Where**: `crates/bench/src/load/accounting.rs:117-135`; same at HEAD
- **What**: `advanced = final − base` per executor, and `advanced <= 0` while the sealer advanced ⇒ `FROZEN`, a hard failure *even in chaos mode* (by design — but the arithmetic can't distinguish "frozen" from "restarted and still replaying"). An executor hard-killed mid-case comes back with `kardamom_executor_block_number` restarting from 0; if the final snapshot (taken only ~3s after drain) lands before it re-passes its baseline, `advanced` is negative and the case fails despite a healthy recovery. The flakiness-campaign memory confirms this exact class ("restarted replica reads gauge 0 during recovery") had to be patched later — chaos.sh probes and the sealer scrape moved to MAX-across-replicas (PR #74 / #69), but the per-executor `advanced` check in `accounting.rs` is unchanged.
- **Still present at HEAD**: partially (sealer-side probes fixed; per-executor FROZEN arithmetic unchanged)
- **Suggested fix**: In chaos mode, treat a negative `advanced` with a *currently advancing* gauge as recovering, e.g. require two final samples a few seconds apart and only flag FROZEN if the second shows no movement.

### F15.6 [low] [quality] — timing assumptions and a known-failing case in the script's own defaults
- **Where**: `deploy/cluster/scripts/chaos.sh:61,80-81,136-146,177` at the commit (`chaos.sh:80-81,299-311,436` at HEAD)
- **What**: (a) The default `CHAOS_CASES` at this commit included `sealer-hard`, documented in the same commit as a known-broken case excluded from CI — so a bare local `./chaos.sh` run was guaranteed to fail. (b) `sleep "${INJECT_DELAY}"` (10s) assumes load is actually flowing before injection — nothing verifies the harness got past pre-generation/first accept, so the kill can precede the first tx. (c) `assert_progress` is a single fixed `sleep 10` window with no timeout on the `docker exec` probes (later PR #74 added `timeout 8` to probes and longer windows for node-failure cases because these exact assumptions flaked).
- **Still present at HEAD**: partially — (a) fixed (defaults no longer include `sealer-hard`); (b) still a bare sleep at HEAD; (c) probe timeouts/windows since hardened
- **Suggested fix**: Gate injection on an observed condition (e.g. `offered > 0` in the harness log or the ingress received counter moving) instead of a fixed sleep.

### F15.7 [nit] [quality] — minor duplication and a misleading doc claim
- **Where**: `crates/bench/src/load/scrape.rs:108-116,197-201` at the commit; `deploy/cluster/scripts/chaos.sh:96-110` vs `deploy/cluster/scripts/ci-cluster.sh`; `crates/bench/src/load/plan.rs:5-8` (HEAD: same for plan.rs and the shell helpers)
- **What**: (a) The scraper fetched each executor's `/metrics` twice per snapshot (`block_at` + `service_up_at`). (b) `on_control`/`running_alloc`/`count_running` are copied from ci-cluster.sh's idioms rather than shared. (c) plan.rs claims the engine submits "each sender's txs in strict nonce order" — only the *pop* order is strict; submits are spawned as concurrent tasks, so wire order (and hence arrival order at ingress) is not. Also, a down sequencer/executor whose fetch fails is silently absent from `service_up`, so the non-chaos "service_up=0 at end" check misses fully-unreachable services.
- **Still present at HEAD**: partially — (a) fixed by the HEAD refactor (single fetch + closure); (b)(c) still present
- **Suggested fix**: Reword the plan.rs doc to "per-sender FIFO pop order"; record `service_up = Some(0)`-equivalent (`None` treated as down in non-chaos mode) when a scrape fails.

## Verdict
An ambitious and largely well-built suite: the open-loop pacer with bounded in-flight, locally-computed tx hashes, per-sender disjoint account/nonce budgeting across stages, drop-accounting via real sequencer counters, unit tests for the pure pieces, and honest documentation of the sealer-SPOF gap are all genuinely good test engineering, and the chaos driver is DRY (one `run_case` table, shared injectors/assertions). But the suite's assertions are weaker than they read: the flagship "must-deliver" gate is structurally incapable of firing (F15.1), the recovery-SLO check can pass before the outage is even visible (F15.3), and the verdict is read while submits may still be in flight (F15.4). Combined with indiscriminate retries against a hard sequencer-drop gate (F15.2) and gauge-reset FROZEN arithmetic (F15.5), it seeded the CI flakiness that the July 2026 campaign later spent multiple PRs fixing — several of those risks are still present at HEAD.
