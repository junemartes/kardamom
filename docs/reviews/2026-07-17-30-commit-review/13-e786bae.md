# 13 e786bae — feat(executor): persist chain state in libMDBX with crash-recovery resume (#61)

## Summary of change
Replaces the executor's in-memory mock state backend with the libmdbx `kardamom-state` StateWriter via three thin adapters (`MdbxSnapshotSource` / `MdbxWriterQueue` / `MdbxWriterSignal`), adds idempotent genesis seeding into a fresh env, and new `--state-dir` / `--state-durability` flags. Phase 2 adds crash-recovery resume: on restart against a non-empty DB the executor replays tx_ordering + tx_data + tx_deposits from the Aeron Archive via replay-merge (`ReplayMergeSubscriber` in crates/log) and skip-counts past the persisted cursor (`ResumePoint { block, record_count }`), re-executing anything sealed during downtime. New archive recorders for tx_data (ingress, per shard) and tx_deposits (da-watcher) behind `--archive-durability`.

The core atomicity design is sound: the writer commits state, headers and all three meta cursors (`last_committed_block`, `last_committed_end_tx_position`, `last_fsynced_b_position`) in a single MDBX RW txn per block (`crates/state/src/writer.rs:203-341`), so the resume point can never tear from applied state. The skip-count arithmetic is clean (`record_count` is the end-count of the resume block; records use `< resume_count`, boundaries use `<= resume_block` and clear `recovering` exactly at `==`), the boundary-alignment invariant is never bypassed during replay, and no new `unsafe` is introduced (the `!Send` rusteron archive handles are correctly confined to one dedicated OS thread).

## Findings

### F13.1 [medium] [logic] — Replay-merge hardcodes `start_position = 0` and only warns on session gaps
- **Where**: `crates/log/src/replay.rs:281` (at commit and at HEAD; the warn heuristic at replay.rs:230-244)
- **What**: `AeronArchiveReplayMerge::new(..., 0 /* start_position */, ...)` requests replay from position 0 of the *latest* recording. If that recording's `start_position != 0` (e.g. the recorder attached after the publication had already offered fragments), Aeron rejects a replay from before the recording's start — the merge fails, surfacing only as F13.4's warn-and-clean-exit. Worse, the code's own restart-detection heuristic is wrong for the common case: a restarted publisher creates a *new session whose recording starts at position 0*, so the "start_position != 0" warning never fires, and replaying only the latest recording silently omits every pre-restart record. The executor then either join-times-out (missing tx_data envelopes are needed even for the skipped prefix — the reader must join every TxRef before the exec thread can skip it) or hits `BoundaryMisaligned`, crash-looping until the state dir is wiped. So an ingress/da-watcher restart at any point in the chain's history permanently breaks executor crash recovery for those streams.
- **Still present at HEAD**: yes (for tx_data / tx_deposits; tx_ordering recovery moved to the Aeron Cluster egress in #67 and no longer uses this path)
- **Suggested fix**: Pass `desc.start_position` instead of 0, and fail hard (not warn) when the resolved recording cannot cover record 0 — or stitch multiple recordings/sessions per stream. Recovery correctness depends on gapless coverage from stream origin.

### F13.2 [medium] [logic] — No guarantee the archive recording covers the stream from record 0; recorder failure is swallowed
- **Where**: `crates/ingress/src/bin/kardamom-ingress.rs` recorder spawn (at commit ~l.166; HEAD l.185-320), `crates/da_watcher/src/bin/kardamom-da-watcher.rs` (HEAD l.112-130)
- **What**: Two gaps. (a) The recorder threads connect to the archive and start recording asynchronously while `main` proceeds to serve JSON-RPC immediately — there is no barrier, so transactions accepted before the recording materialises are published but never archived. Since recovery replays from record 0 and needs *every* envelope (even skipped-prefix records must join in the reader), any birth-of-stream gap permanently breaks later executor recovery. (b) `run_tx_data_recorder` / `run_tx_deposits_recorder` errors are only `tracing::error!`-logged; the process keeps serving with `--archive-durability` silently ineffective.
- **Still present at HEAD**: yes
- **Suggested fix**: Block RPC/publishing until the recording is confirmed active (or record with `AUTO_START` on the publication channel), and treat recorder startup failure as fatal when `--archive-durability` was requested.

### F13.3 [medium] [logic] — Recovery gate `last_committed_block > 0` leaves a crash-before-first-commit window
- **Where**: `crates/executor/src/bin/kardamom-executor.rs` (at commit, resume gate; at HEAD l.223 and l.246)
- **What**: Replay-merge recovery is engaged only when the durable cursor shows a committed block. If the executor crashes (or is killed) after the sealer/ingress have published records but before block 1 durably commits — or simply starts later than the first published record — restart takes the fresh-start path with *live* subscribers, joins mid-stream, and the reader/exec invariants (`OutOfOrderTx` / join timeout / `BoundaryMisaligned`) make it crash-loop; restarting never helps because the DB stays at block 0. Recovery keyed on "DB non-empty" conflates "fresh chain" with "crashed at block 0".
- **Still present at HEAD**: partially — tx_ordering is now gapless via the cluster `ReplayCursor::genesis()`, but the tx_data / tx_deposits archive-replay path is still gated on `resume.is_some()`, so the mid-stream-join failure mode remains for envelopes.
- **Suggested fix**: When the transport supports replay, use the archive/replay path whenever the stream may already contain records (e.g. always in cluster mode), not only when `last_committed_block > 0`.

### F13.4 [low] [logic] — Replay/recovery failures surface as a warn + clean (exit 0) shutdown
- **Where**: `crates/log/src/replay.rs` (thread body error → `warn!`, at commit l.130-137; HEAD ~l.150) plus exec loop `Err(_) => return Ok(())` (`crates/engine/src/actor.rs:354-356` at HEAD)
- **What**: A fatal replay-merge error (archive error, decode failure, 60 s no-progress `has_failed()`) ends the poll thread with a *warn*-level log and closes the channel; the executor's exec loop maps a closed reader channel to `Ok(())`, and `main` exits 0. A failed crash recovery is therefore indistinguishable from a clean shutdown to an orchestrator keyed on exit status, and the error is easy to miss in logs.
- **Still present at HEAD**: yes
- **Suggested fix**: Log at error level and propagate replay-thread failure to the consumer (e.g. an `Err`/poisoned-channel variant) so the executor exits non-zero when its input stream died abnormally.

### F13.5 [low] [logic] — Receipts and the sealed Boundary are published before the durable commit ack
- **Where**: `crates/executor/src/actor.rs` boundary arm at commit (submit → send `ExecToCommit::Boundary` → `wait_committed`); `crates/engine/src/actor.rs:549-556` at HEAD; per-tx receipts sent at execute time (HEAD l.408, l.459)
- **What**: Receipts stream out per tx and the boundary is forwarded to the tx_receipts publisher *before* `wait_committed` returns. A crash in that window means downstream (ingress ack path) has observed receipts/boundaries for state that was never durably committed; recovery then re-executes those records and re-publishes byte-identical duplicates. With the in-memory backend this ordering was moot; now it defines the system's at-least-once semantics. Safe only as long as every tx_receipts consumer is idempotent on `tx_idx` (and worse under `safe-no-sync`, where `wait_committed` isn't actually durable).
- **Still present at HEAD**: yes
- **Suggested fix**: Either move the Boundary send (and ideally receipt batch release) after `wait_committed`, or document the duplicate-delivery contract on tx_receipts and verify ingress dedups by `tx_idx`.

### F13.6 [low] [logic] — `resolve_recording` only pages the first 100 recordings
- **Where**: `crates/log/src/replay.rs` `list_recordings_for_uri(0, 100, ...)` (at commit; HEAD l.398-404)
- **What**: The catalog is listed from record id 0 with a page of 100 and the max matching id wins. Recording ids are archive-global across all streams (10+ recorders per boot, one new recording per process restart), so after enough restarts the newest recording for a stream falls beyond the first page and a stale session is resolved — replaying old data and crash-looping on misalignment.
- **Still present at HEAD**: yes
- **Suggested fix**: Page through the catalog (loop `from_record_id += page`) until exhausted, or use `find_last_matching_recording`.

### F13.7 [low] [logic] — Genesis drift across restarts is undetected
- **Where**: `crates/state/src/genesis.rs` `seed_genesis` (at commit and HEAD)
- **What**: Seeding is gated on the presence-only `genesis_applied` flag. If the operator changes the `--chain` genesis TOML (or points a node at the wrong state dir), the new allocations are silently ignored — no hash/fingerprint of the seeded genesis is persisted or compared, so two replicas can run divergent genesis state without any error.
- **Still present at HEAD**: yes
- **Suggested fix**: Persist a digest of the genesis alloc under a meta key at seed time and fail startup when a supplied `--chain` file's digest differs.

### F13.8 [nit] [quality] — Misleading crash-safety comment in `seed_genesis`
- **Where**: `crates/state/src/genesis.rs` ("Flag last so a crash mid-seed leaves the env un-flagged and the next start re-seeds cleanly"; HEAD genesis.rs:108)
- **What**: All puts and the flag are in one MDBX RW txn; a crash mid-seed aborts the entire txn regardless of put order. The comment implies a non-atomic ordering matters, which misdescribes the (correct) atomicity model.
- **Still present at HEAD**: yes
- **Suggested fix**: Reword: the flag is in the same atomic txn as the allocations; ordering is irrelevant.

## Verdict
A well-built commit on its core promise: the persisted resume point and applied state are committed in one atomic MDBX transaction, the skip-count replay logic is genuinely off-by-one-free (verified against the exec loop and its four targeted unit tests), the alignment invariant is preserved during replay, DB failures fail-stop the writer and surface through the closed snapshot channel, and the `!Send` Aeron FFI handles are properly thread-confined with no new unsafe. The weaknesses are all at the edges of the recovery story rather than in the state machine: the archive-coverage assumptions (single uninterrupted publisher session, recording present from record 0, first-100 catalog page) are fragile and mostly fail as opaque crash-loops or — worse — a warn-plus-exit-0, and the receipts-before-durable-ack ordering quietly defines an at-least-once contract that is nowhere documented. None of these corrupt state; they degrade the availability of the recovery feature itself and deserve follow-up hardening.
