# 01 70d0823 — fix(validator): catch-up mode — skip aged-out BAL waits when far behind live (#78)

## Summary of change
Adds a catch-up fast path to `BalBuffer::take()`: if the highest buffered block ("live head") is more than `BACKLOG_LOOKBEHIND` (16) blocks ahead of the requested block, the BAL is treated as aged out of the tx_bal term buffer and `take()` returns `None` immediately (commit unverified) instead of blocking up to the 5s BAL window per block. This lets a cold-started or long-lapsed validator catch up instead of crawling. Also adds a `validator-lapse` chaos case (docker-pause the validator 30s under load, assert it resumes verifying, coverage held, no divergence) and wires it into the chaos-sequencer CI shard.

## Findings

### F01.1 [medium] [quality] — Chaos-case comments describe the discarded side-stream refetch design
- **Where**: deploy/cluster/scripts/chaos.sh:174-182 and 595-598 (at the commit and at HEAD; HEAD == this commit)
- **What**: The `run_validator_lapse` header comment says "the archive-backed refetch source must redeliver the missed BALs" and "Asserts: refetch actually fired (bal_refetched grew)", and the `run_case` dispatch comment says "assert its side-stream refetch recovers full verification coverage". No refetch mechanism exists (the commit message itself says the side-stream-refetch prototype was discarded), no `bal_refetched` metric exists anywhere in `crates/validator/`, and the function asserts nothing about refetch. The actual recovery mechanism is the live term buffer draining on unpause. A future reader will search for a refetch subsystem that does not exist.
- **Still present at HEAD**: yes
- **Suggested fix**: Rewrite both comments to describe the real mechanism (term-buffer drain on resume + catch-up skip for gaps larger than the term buffer) and delete the `bal_refetched` assertion claim.

### F01.2 [medium] [security] — Commit churns tracked build artifacts (.gradle caches, built jar)
- **Where**: cluster/sealer-service/.gradle/** (8 files) and cluster/sealer-service/core/build/libs/core-0.1.0.jar at the commit; all still tracked at HEAD (e.g. /home/dev/kardamom-review/cluster/sealer-service/.gradle/8.7/fileHashes/fileHashes.bin, .../core/build/libs/core-0.1.0.jar)
- **What**: A validator fix commit carries binary churn in Gradle local build caches, lockfiles, `file-system.probe`, and a compiled jar under `core/build/libs/`. These are machine-local build outputs that were evidently committed earlier and keep getting re-modified by every build (`git add -A` hazard — the same failure mode #74 fixed for the docker staging jar). They bloat history on every commit that touches them and can leak local environment details.
- **Still present at HEAD**: yes
- **Suggested fix**: `git rm -r --cached cluster/sealer-service/.gradle cluster/sealer-service/*/build` and gitignore `.gradle/` and `build/` under `cluster/sealer-service/` (keep `gradle/wrapper/gradle-wrapper.jar`).

### F01.3 [low] [logic] — Warm-up loop can time out yet log "warmed up" and proceed
- **Where**: deploy/cluster/scripts/chaos.sh:196-206 (at the commit and HEAD)
- **What**: If the validator never reaches the warm-up condition within 150s, the `while` loop exits normally and the script logs "validator-lapse: warmed up (...)" and pauses anyway. The case then fails later with a misleading downstream message ("did not resume verifying") when the real problem was that it never verified pre-pause; the "warmed up" log line actively misdirects triage.
- **Still present at HEAD**: yes
- **Suggested fix**: Track whether the warm-up condition was actually met and `fail "validator-lapse: never warmed up (...)"` when the 150s budget expires.

### F01.4 [low] [logic] — Catch-up skip inert while the buffer is empty; late BALs for skipped blocks leak
- **Where**: crates/validator/src/lib.rs:157-161 (at the commit and HEAD)
- **What**: Two edges of the new fast path. (a) The skip needs a buffered head, so until the first live BAL is inserted (subscriber not yet joined, or a quiet chain) every backlog block still waits the full 5s window — the crawl the commit fixes briefly persists at startup. (b) `take()` returning `None` (skip or timeout) leaves any later-arriving BAL for that block in the `BTreeMap` forever; nothing prunes entries below the commit cursor, so a validator that skipped N blocks whose BALs then replay (or a lost-then-late BAL) accretes dead entries for the process lifetime. Both are bounded in practice (ordered stream makes (b) rare; (a) ends at first insert), hence low.
- **Still present at HEAD**: yes
- **Suggested fix**: In `insert()` (or after each commit), drop entries below the last-committed block; optionally seed the head from the subscriber's first image position so the skip can fire before the first insert.

## Verdict
The core fix is small, well-commented, and correct for its stated scenario: the skip only fires when the BAL is provably absent behind a buffered head on an ordered stream, so a caught-up validator's behavior is unchanged, and the deadline-not-per-wakeup wait semantics are preserved. The chaos case is a genuine end-to-end regression net. The blemishes are around the edges: the chaos-case comments document a design the same commit says was discarded (F01.1), and the commit drags along tracked Gradle build-cache binaries that should never have been in the repo (F01.2).
