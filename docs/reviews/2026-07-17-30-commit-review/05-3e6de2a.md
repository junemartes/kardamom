# 05 3e6de2a — chore: drop accidentally-committed cluster jar; gitignore the staging path (#74)

## Summary of change
Removes `deploy/cluster/docker/kardamom-cluster-node.jar` (swept into #72 by a broad `git add -A`) and gitignores the staging path. The squashed PR also carries several chaos-suite hardening fixes (sealer-boundary probe takes MAX across executors instead of first-responder; 180s post-recovery and in-case windows for node-failure cases; `timeout 8` around every `docker exec curl` probe), an executor fix (always bound the tx_data join wait — 60s on fresh starts — so a raced multicast join fails loudly instead of freezing a replica), and a cluster-adapter fix (replay requests use the retrying `publish_bytes` instead of `publish_best_effort`, plus `cluster REPLAY ... served=N` stdout logging in the Java service).

## Jar verification
- **Gone from the tree at HEAD**: yes — `deploy/cluster/docker/` contains only Dockerfiles and `dockerignore.example`; `.gitignore` there covers `kardamom-cluster-node.jar`.
- **Still in git history**: yes — the blob is reachable at `52a32a2:deploy/cluster/docker/kardamom-cluster-node.jar` (2,502,100 bytes; the "45MB" in the commit message overstates the stored blob size). See F05.1.

## Findings

### F05.1 [low] [security] — Removed jar remains in git history (repo bloat; content benign)
- **Where**: blob at 52a32a2:deploy/cluster/docker/kardamom-cluster-node.jar (2.5MB); removed from the tree by this commit
- **What**: `git rm` only removes the file going forward; every clone still carries the 2.5MB blob. Content-wise it is the project's own compiled sealer-service shadowJar — a build artifact of public first-party code, not credentials — so this is repository bloat, not a disclosure. Severity would rise only if the jar embedded secrets/config, which nothing suggests.
- **Still present at HEAD**: yes (in history, by nature)
- **Suggested fix**: Acceptable to live with; if history size matters, rewrite with `git filter-repo --path deploy/cluster/docker/kardamom-cluster-node.jar --invert-paths` and force-push (coordinate with all clones).

### F05.2 [medium] [quality] — Cleanup incomplete: other build artifacts remain tracked at HEAD
- **Where**: cluster/sealer-service/.gradle/** (build caches, lockfiles, `file-system.probe`), cluster/sealer-service/core/build/libs/core-0.1.0.jar, core/build/test-results/**, core/build/tmp/** (all tracked at HEAD)
- **What**: This commit fixes exactly one `git add -A` casualty but leaves the same class of artifact tracked elsewhere: Gradle local caches and a compiled jar under `cluster/sealer-service/`. They churn on every local build — commit 70d0823 (a validator fix) re-modifies 10 of these binaries — so the hazard the commit message identifies is still live.
- **Still present at HEAD**: yes
- **Suggested fix**: `git rm -r --cached cluster/sealer-service/.gradle 'cluster/sealer-service/*/build'` and add `.gradle/`, `build/` to a gitignore under `cluster/sealer-service/` (keep `gradle/wrapper/gradle-wrapper.jar`).

### F05.3 [low] [logic] — Retrying replay-request publish can block the session loop up to 10s; error discarded
- **Where**: crates/cluster-adapter/src/live.rs:317 (at HEAD; ~:312 at the commit)
- **What**: `PubHandle::publish_bytes` blocks the caller for up to 10s waiting for the Aeron-thread ack (crates/log/src/aeron_live.rs:810-822). The call sits in `run_session`'s single loop, which also drains egress frames (step 1) and emits connect/keep-alive frames (step 2, `driver.poll_outbound`). Under exactly the churn scenario the fix targets (backpressured ingress publication during mass reconnects), each 3s resend can now stall the loop up to 10s, delaying keep-alives — risking session timeouts — and pausing egress processing. The `Result` is also discarded (`let _ =`), so a timed-out publish is indistinguishable from a sent one; only the next 3s resend saves it.
- **Still present at HEAD**: yes
- **Suggested fix**: Use a bounded retry with a short deadline (e.g. 1-2s) or log the error on failure so a persistent publish failure is visible; alternatively make the ack wait non-blocking and check it on the next loop pass.

### F05.4 [nit] [quality] — Fresh-start join timeout (60s) exceeds the resume timeout (30s), inverting the stated rationale
- **Where**: crates/executor/src/bin/kardamom-executor.rs:432-435 (at the commit and HEAD)
- **What**: The pre-existing comment says the join timeout is "relaxed generously while resuming" from the tight 100ms live default; the new code gives fresh starts 60s and then *tightens* to 30s when resuming. Both bounds are sound (the point is that no wait is unbounded), but the resulting fresh > resume ordering reads backwards against the adjacent comment and invites a "fix" that reintroduces the bug.
- **Still present at HEAD**: yes
- **Suggested fix**: One sentence in the comment on why a fresh start warrants the longer bound (or unify both to 60s).

## Verdict
The headline chore is done correctly (jar out of the tree, staging path ignored) and the piggybacked fixes are individually well-motivated with unusually good forensic commit messages; the MAX-across-replicas probe, `timeout 8` transport bound, and always-bounded join wait each close a real observed failure mode. Two caveats: the cleanup stops one directory short of the same artifact class it set out to fix (F05.2), and swapping to the blocking `publish_bytes` on the session thread trades a dropped-message bug for a potential 10s loop stall under the very backpressure it fires in (F05.3). The jar persists in history but its content is benign (F05.1).
