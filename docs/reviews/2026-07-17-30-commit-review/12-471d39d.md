# 12 471d39d — active/active ingress + Aeron Cluster (Raft) sealer (cluster-only) (#67)

## Summary of change
Replaces the standalone Rust sealer (deleted crate + deploy artifacts) with a 3-member JVM Aeron Cluster (Raft) as the sole tx_ordering orderer: a deterministic `CanonicalSealerState` state machine (dedup window, canonical count, boundary ticks, snapshots) wrapped in a `SealerClusteredService`, plus a hand-written Rust SBE cluster client (`kardamom-cluster-client`) and a live gateway (`kardamom-cluster-adapter`) wired into sequencer (publish), executor (subscribe), and ingress (on-quorum watermark). Simultaneously makes ingress active/active: `TxRef.tx_data_session_id` + a session-keyed executor join buffer disambiguate concurrent publishers, `correlation_id` is namespaced by `ingress_id` ((id<<48)|seq), and tx_receipts move from per-ingress MDS to a shared multicast group with local dedup. Deploy, chaos suite, contract checker, and CI workflows are migrated to the cluster topology.

## Findings

### F12.1 [high] [logic] — Snapshot restore polls raw fragments without a fragment assembler; realistic snapshots are truncated
- **Where**: `cluster/sealer-service/service/src/main/java/io/kardamom/sealer/cluster/SealerClusteredService.java` (loadFromSnapshot, ~line 205 at commit; lines 261–283 at HEAD)
- **What**: `loadFromSnapshot` calls `snapshotImage.poll(handler, 1)` with a raw `FragmentHandler` and takes the FIRST fragment as the whole snapshot. `onTakeSnapshot` offers the state as a single Aeron message; with the default `dedupCapacity` 8192 the snapshot is ~262 KB (28 + 8192×32), far above the MTU, so Aeron delivers it as many fragments unless an `ImageFragmentAssembler` is used. On restore, `CanonicalSealerState.load` then parses a truncated first fragment: the header/counters survive but `idCount` exceeds the buffer → `BufferUnderflowException` at member start (or, for mid-size states, a silently smaller dedup window). Snapshots only round-trip while the dedup window holds ≲40 ids; no in-cluster test takes a snapshot (SealerClusterFailoverTest and SealerReplayTest explicitly avoid it), so this is untested and broken for any realistic state.
- **Still present at HEAD**: yes
- **Suggested fix**: Wrap the poll handler in `new ImageFragmentAssembler(handler)` (and mirror it with chunked/`tryClaim` framing in `onTakeSnapshot` if snapshots can exceed max message length), and add a snapshot-restart TestCluster case with >MTU of dedup state.

### F12.2 [high] [logic] — Failed/empty snapshot image silently restarts the member at genesis (state divergence instead of fail-stop)
- **Where**: same `loadFromSnapshot` (commit ~line 210; HEAD lines 272–281), plus `onTakeSnapshot` (commit ~line 232; HEAD lines 234–241)
- **What**: If the snapshot image closes/EOFs before a fragment arrives, `loadFromSnapshot` returns a fresh `CanonicalSealerState` at genesis instead of failing — a member that couldn't read its snapshot rejoins with `canonicalCount=0`, `blockNumber=1` and an empty dedup window while the rest of the cluster (and the log the consensus module replays *after* the snapshot point) assumes the snapshotted state, i.e. deterministic-state-machine divergence. The write side compounds it: `onTakeSnapshot`'s retry loop exits silently on any non-retryable offer result (`NOT_CONNECTED`/`CLOSED`), recording an empty snapshot with no error.
- **Still present at HEAD**: yes
- **Suggested fix**: Treat an unreadable/empty snapshot image and a failed snapshot offer as fatal (throw), letting the consensus module abort the snapshot/recovery rather than fabricating genesis state.

### F12.3 [high] [logic] — Claimed tx_ordering crash-recovery replay did not exist: a (re)connecting client silently lost committed records
- **Where**: `crates/executor/src/bin/kardamom-executor.rs` (comment block at the cluster subscription, commit lines ~296–312), `crates/cluster-adapter/src/live.rs`, `crates/cluster-client/src/session.rs` (at commit)
- **What**: The executor wiring asserts "crash-recovery replay of the canonical stream is handled inside the cluster client … the cluster client replays the canonical stream on reconnect", but no replay existed anywhere in the commit: Aeron Cluster egress only delivers from session-open onward, and `SessionDriver`/`live.rs` had no replay request, no cursor, and no catch-up. An executor restart (or a session re-established after leader failover) permanently missed every record committed while it was detached — surfacing as join timeouts / `BoundaryMisaligned` / silently divergent state. tx_data/tx_deposits archive replay was kept, making the gap asymmetric and easy to miss.
- **Still present at HEAD**: no (fixed by 52a32a2, PR #72 — F3 replay protocol: `KIND_REPLAY_REQUEST` / `REPLAY_UNAVAILABLE` / `REPLAY_DONE`, retained-frame buffer, cursor-driven client resend)
- **Suggested fix**: n/a (fixed); worth noting the retention buffer is still not snapshotted (v1), so post-snapshot-restart members refuse pre-restart ranges — documented degradation.

### F12.4 [medium] [logic] — Session driver had no connect retry/timeout; a lost connect frame stranded the client forever
- **Where**: `crates/cluster-client/src/session.rs` (`poll_outbound`, commit lines ~150–190); `crates/cluster-adapter/src/live.rs` `run_session` (commit line ~348)
- **What**: At the commit, the single `SessionConnectRequest` was emitted once (`pending_connect` consumed) and sent via `publish_best_effort` on a publication that had typically just been opened and was not yet connected — so the frame could be dropped, and with no connect timeout/re-send the driver sat in `Connecting` forever (`wrap_app` → `None` → sequencer sees permanent `Backpressure`, executor egress never opens). `Failed` was likewise terminal with no reconnect. Similarly, if `open_leader_pub` failed at startup, `run_session` logged an error and returned — the service kept running with a dead session thread and no propagated error.
- **Still present at HEAD**: partially — connect timeout/re-send, `Failed`→reconnect backoff and member rotation were added later (HEAD session.rs lines 160–196), but the initial `open_leader_pub` failure in `run_session` still just logs and returns, leaving the owning binary alive with a silently dead cluster session.
- **Suggested fix**: Make `run_session`'s initial-publication failure surface to the caller (fail startup) or retry with rotation like the connected path does.

### F12.5 [medium] [logic] — Cluster egress offer busy-loop could stall the replicated state machine on one slow client
- **Where**: `SealerClusteredService.offerToSession` (commit lines ~316–322)
- **What**: At the commit, `offerToSession` spun `do { offer } while (BACK_PRESSURED || ADMIN_ACTION)` with no deadline, on the single clustered-service thread, once per client session per record/boundary. One live-but-not-draining client (frozen ingress, wedged executor) back-pressures its egress publication indefinitely and blocks log processing for the whole cluster — the exact "one slow subscriber freezes everyone" pathology this migration was meant to remove. `NOT_CONNECTED` was also treated as terminal-but-ignored, silently dropping frames to zombie sessions.
- **Still present at HEAD**: no (fixed by 52a32a2 — bounded `OFFER_DEADLINE_NS` then `session.close()`, and NOT_CONNECTED joins the deadline-then-close path)
- **Suggested fix**: n/a (fixed).

### F12.6 [medium] [logic] — `CanonicalSealerState.load` does not validate snapshot size against capacity or remaining bytes
- **Where**: `cluster/sealer-service/core/src/main/java/io/kardamom/sealer/CanonicalSealerState.java` (`load`, commit lines ~195–219; HEAD lines ~196–218)
- **What**: `load(snapshot, dedupCapacity)` inserts `idCount` ids without checking `idCount <= dedupCapacity` (a snapshot taken with a larger configured window, or a capacity lowered across a restart, yields an oversized window that `firstSeen` shrinks by only one entry per insert — dedup behaviour then differs from a fresh state with the same config, a determinism hazard if members ever disagree on `-Dkardamom.cluster.dedupCapacity`). A truncated buffer surfaces as a raw `BufferUnderflowException` rather than a descriptive error (this is also the failure mode of F12.1).
- **Still present at HEAD**: yes
- **Suggested fix**: In `load`, validate `idCount` against both `dedupCapacity` and `buf.remaining()/CANONICAL_ID_LEN`, throwing `IllegalArgumentException` with context; evict-from-front if a smaller capacity is intentional.

### F12.9 [low] [quality] — `enabled = true` config knob is parsed, documented in deploy files, but ignored
- **Where**: the three `ClusterConfig`s (`enabled` field, e.g. `crates/executor/src/config.rs:34-36` at commit); set `= true` in `deploy/cluster/config/{executor.toml,ingress.toml,sequencer.toml.tpl}`
- **What**: Every struct carries `enabled: bool` marked "IGNORED — cluster mode is the only mode", yet the shipped deploy configs set `enabled = true`, implying it does something. An operator setting `enabled = false` gets a service that still connects to the cluster (or, with an empty `[cluster]` section, a service whose session thread dies silently — see F12.4). Misleading knob, and with `ingress_endpoints` defaulting to `""` a missing section fails only at runtime with a log line instead of a config validation error.
- **Still present at HEAD**: yes
- **Suggested fix**: Drop `enabled` (or make `false` a hard startup error), and validate `ingress_endpoints`/`egress_channel` non-empty at startup for the services that require them.

### F12.12 [nit] [quality] — Ingress-side silent drops: malformed/too-short cluster frames only logged, no metric
- **Where**: `SealerClusteredService.onSessionMessage` (short-frame early return, commit ~line 174); `crates/executor/src/reader/cluster.rs:47-52`; `crates/ingress/src/cluster.rs:55-60`
- **What**: Undersized ingress envelopes and undecodable egress frames are dropped with at most a `tracing::warn!`. On the Java side there is no counter/log at all. These are "should never happen" paths on an authoritative stream, but if a framing mismatch ever ships (the Java/Rust envelope is kept in lockstep by hand — see the TODO(envelope) comment) the symptom would be silent record loss diagnosable only by warn-level log volume.
- **Still present at HEAD**: yes

## Verdict
An unusually large but well-structured migration: the deterministic core (`CanonicalSealerState`), the sans-IO `SessionDriver`, the session-keyed join buffer, and the correlation-id namespacing are all cleanly designed and genuinely well-tested (including a real in-JVM Raft failover test and a K-replica ingress harness), and the deploy/chaos/CI surface was migrated coherently, including a sharp DashMap self-deadlock fix in the receipt cache. However, the commit shipped with its two hardest distributed-systems edges unfinished: the claimed cluster-side tx_ordering replay did not exist (F12.3, fixed two commits later in #72 along with the egress busy-loop stall F12.5 and the missing connect retry F12.4), and the snapshot save/restore path is still broken today for any realistically sized state (F12.1) with a divergence-inducing silent genesis fallback (F12.2) — mitigated only by the fact that nothing currently triggers snapshots routinely. The actionable work at HEAD is concentrated in the snapshot path, plus a handful of hygiene items (committed `.pyc`, triplicated `ClusterConfig`, ignored `enabled` knob, contract-checker ingress gap).
