# 06 637f683 — feat(withdrawals): L2→L1 off-ramp (optimistic, ZK-challenge-ready) (#71)

## Summary of change
Squashed PR building the L2→L1 withdrawal path on top of the new validator/MPT-state-root work: an L2 predeploy `L2ToL1MessagePasser` (locks ETH, emits `MessagePassed`), an L1 `WithdrawalOutputOracle` (permissioned attester posts output roots; permissioned challenger may delete within a 1-day window), and `ETHLockbox.finalizeWithdrawal` (positional keccak-Merkle inclusion proof against an attested, finalizable output root, replay-guarded, then ETH release). Rust side adds `kardamom-types::withdrawals` (leaf/tree/proof/output-root, byte-matching Solidity), a validator `attester` module (collect leaves from re-executed blocks, build+post output roots), and deployer support (new ContractId, predicted proxy addresses, a `proxy_salt` abi-encoding fix). Also includes the validator/engine/BAL/trie work of PR #7x plus Foundry, Rust unit, and anvil e2e tests.

Cross-language encoding was checked byte-for-byte and is consistent: leaf = `keccak(abi.encode(nonce,sender,target,value))` (Rust offsets 0/44/76/96 in a 128-byte buffer match), output root = `keccak(version ++ stateRoot ++ withdrawalsRoot)` (65 bytes both sides), Merkle direction convention (even index → node left) matches, and `message_passed_topic0()` matches the event signature. The challenge/finalize windows are mutually exclusive at every timestamp (`deleteOutput` requires `now < t+window`, `isFinalizable` requires `now >= t+window`). CEI is respected in `finalizeWithdrawal` (replay flag set before the transfer).

## Findings

### F06.1 [medium] [logic] — Successful challenge permanently strands every honest withdrawal in the challenged range
- **Where**: contracts/src/L1/WithdrawalOutputOracle.sol:94 (`proposeOutput` monotonicity check counts deleted outputs) + crates/validator/src/attester.rs:52 (`collect_withdrawal_leaves` is per-block-range only); same lines at HEAD
- **What**: `proposeOutput` reverts `NonMonotonicBlock` when `l2BlockNumber <= _outputs[n-1].l2BlockNumber`, and the comparison includes **deleted** outputs. After the challenger deletes the latest output covering blocks ≤ B, a corrected output for the same range (l2BlockNumber == B) can never be posted. Since the attester builds each output's withdrawals tree only from that range's `MessagePassed` leaves, the withdrawals in a challenged range are never re-attested: users' ETH is locked on the L2 predeploy and can never finalize on L1. The dev comment on `deleteOutput` acknowledges the missing "roll back later outputs" semantics, but not this re-proposal deadlock. Amplified by F06.6: a compromised/buggy challenger can strand ranges at will.
- **Still present at HEAD**: yes
- **Suggested fix**: Exclude deleted outputs from the monotonicity check (track `latestNonDeletedL2Block`), or require the replacement output for a deleted index; on the attester side, carry unattested leaves forward into the next output after a deletion.

### F06.2 [medium] [security] — ~200 KB of Gradle build outputs, .class files and a .jar committed; still tracked at HEAD despite the commit message claiming they were dropped
- **Where**: cluster/sealer-service/.gradle/** and cluster/sealer-service/core/build/** (19 binary files incl. `core/build/libs/core-0.1.0.jar`, `.class` files, `executionHistory.bin`); same paths tracked at HEAD (`git ls-files` confirms)
- **What**: The final squashed sub-commit says "drops gradle build outputs accidentally committed to the original branch", but the squash *adds* them (all show `Bin 0 -> N bytes` in the stat). The later cleanup 3e6de2a removed only a different jar (`deploy/cluster/docker`). Committed opaque binaries are unauditable, bloat the repo, and `executionHistory.bin`/`fileHashes.bin` leak local build-host paths.
- **Still present at HEAD**: yes
- **Suggested fix**: `git rm -r cluster/sealer-service/.gradle cluster/sealer-service/core/build` and add `.gradle/`, `build/` to `cluster/sealer-service/.gitignore`.

### F06.3 [medium] [quality] — Attester is never wired into the validator binary; the production off-ramp is inert
- **Where**: crates/validator/src/attester.rs (library only); crates/validator/src/bin/kardamom-validator.rs at HEAD has no reference to `attester`/`OutputPoster`
- **What**: The commit message presents the attester as the validator's L1-facing seam, but no driver loop exists: nothing in the validator binary collects leaves per committed range, builds the output, or posts it. Outputs are only ever posted by tests (`withdrawal_e2e.rs` calls `OutputPoster` manually). A deployment of this code has a withdrawal path that can never finalize because no outputs reach the oracle.
- **Still present at HEAD**: yes
- **Suggested fix**: Wire an attestation task into `kardamom-validator` main (after each committed block/range: `collect_withdrawal_leaves` → `build_output` → `propose_output`, resuming from `output_count()`), or state explicitly in docs that milestone 1 has no automatic attestation.

### F06.4 [low] [logic] — Deployer panics (index out of bounds) when deploying KardamomL2Settlement without matching `--l2-minter`
- **Where**: crates/deployer/src/main.rs:239 (`ContractId::KardamomL2Settlement => encode_address_arg(l2_minters[i])`), guard at main.rs:124 now conditional on EthLockbox; same at HEAD
- **What**: The `l2_chain_ids.len() == l2_minters.len()` check was relaxed to apply only when `EthLockbox` is among the deployed ids, but the `KardamomL2Settlement` arm still indexes `l2_minters[i]`. `deploy KardamomL2Settlement --l2-chain-id 42` with no `--l2-minter` panics instead of a clean error. Also, the L2 minter is silently reused as the settlement contract's `_l1Batcher` init arg, which is at best confusing.
- **Still present at HEAD**: yes
- **Suggested fix**: Extend the count check to any id that consumes `l2_minters`, or add a dedicated `--l1-batcher` flag for settlement and error out when missing.

### F06.5 [low] [security] — Merkle verifier has no leaf/internal-node domain separation and ignores high bits of `leafIndex`
- **Where**: contracts/src/L1/ETHLockbox.sol:138 (`_merkleRoot`), mirrored in crates/types/src/withdrawals.rs (`recompute_root`); same at HEAD
- **What**: Internal nodes and leaves are both plain `keccak256` with no prefix, proof depth is unbounded/unbound to the tree, and `leafIndex` bits beyond `proof.length` are ignored (many indices verify the same proof). Today this is **not exploitable**: the leaf hash is computed on-chain from `wtx` (its 128-byte `abi.encode` preimage cannot collide with a 64-byte internal-node preimage), and the replay guard is keyed on the leaf hash, not `(outputIndex, leafIndex)`. But the safety rests on the leaf preimage length; any future leaf-format change (e.g. a 64-byte packed leaf) would open the classic second-preimage forgery.
- **Still present at HEAD**: yes (hardening, not a live vulnerability)
- **Suggested fix**: Domain-separate (`keccak(0x00 ++ leafdata)` vs `keccak(0x01 ++ l ++ r)`) or commit the tree depth in the output and require `proof.length == depth` and `leafIndex < 2**depth`.

### F06.6 [low] [security] — No init validation and no key rotation for attester/challenger/window
- **Where**: contracts/src/L1/WithdrawalOutputOracle.sol:60-66 (`initialize`), contracts/src/L1/ETHLockbox.sol:61; same at HEAD
- **What**: `initialize` accepts zero addresses and a zero `finalizationWindow` (window 0 ⇒ instantly finalizable outputs, challenge impossible), and there are no setters: a leaked attester key can post fraudulent roots forever (challenger is the only backstop) and a leaked challenger key can delete every output within its window — which, combined with F06.1, permanently strands funds. Acceptable for a permissioned milestone but the contract offers no recovery short of a UUPS upgrade via the factory.
- **Still present at HEAD**: yes
- **Suggested fix**: Require non-zero attester/challenger and a minimum window in `initialize`; add factory-gated rotation setters.

### F06.7 [nit] [quality] — `decode_message_passed` trusts the event-carried withdrawal hash and tolerates trailing data
- **Where**: crates/types/src/withdrawals.rs:37-44; same at HEAD
- **What**: The attester takes the leaf from `data[32..64]` instead of recomputing `withdrawal_leaf(nonce, sender, target, value)` from the topics+data it already has; `data.len() < 64` (not `!= 64`) also accepts malformed logs. Safe today because the predeploy computes the hash itself, but a recompute-and-compare would catch predeploy/bytecode drift (the runtime bytecode is duplicated by hand in chains/dev-withdrawals.toml, a documented drift risk) for free.
- **Still present at HEAD**: yes
- **Suggested fix**: Recompute the leaf from the decoded fields and require equality with the event's hash; use `data.len() != 64`.

### F06.8 [nit] [quality] — ETHLockbox `initialize` signature changed with no reinitializer for existing proxies
- **Where**: contracts/src/L1/ETHLockbox.sol:61; crates/deployer/src/ids.rs (`initialize(address,address)`); same at HEAD
- **What**: Already-deployed lockbox proxies (initialized with the one-arg version) can be upgraded to this implementation but can never set `outputOracle` (`initializer` blocks re-entry; no `reinitializer(2)` provided), leaving them deposit-only forever. Also `full_withdrawal_finalize_and_challenge`, the only cross-language finalize e2e, is `#[ignore]`d for a receipt-watcher flake (the Solidity side is covered by Foundry, so exposure is limited).
- **Still present at HEAD**: yes
- **Suggested fix**: Add a `reinitializer(2) setOutputOracle`-style migration entry point (factory-gated), or document that pre-existing lockboxes must be redeployed.

## Verdict
The core cryptographic and value-moving logic is solid for a milestone-1 permissioned design: Rust/Solidity byte encodings match exactly (confirmed by real cross-language tests against a deployed contract), the challenge and finalization windows are airtight at the boundary, the replay guard is global on the leaf hash and set before the transfer, and access control on the oracle is correct. The genuine weaknesses are around the edges rather than the happy path: a successful challenge deadlocks re-attestation of the affected range (F06.1), the attester exists only as a library so the production off-ramp cannot actually run (F06.3), and the commit ships ~200 KB of Gradle binaries it claims to have removed (F06.2). The Merkle-verifier hardening and init-validation items are prudent follow-ups before the "swap in a SNARK verifier" phase 2. Test coverage (48 Foundry tests plus Rust unit and anvil e2e) is genuinely strong for the code that exists.
