# 03 4945670 — fix(obs): run the Prometheus exporter on a dedicated thread (issue #76 hypothesis 1) (#77)

## Summary of change
Rebuilds `kardamom_obs::init` so the Prometheus recorder+exporter is built and run on a dedicated `obs-exporter` OS thread with its own single-threaded tokio runtime, decoupling `/metrics` liveness from the service runtime (issue #76 hypothesis: a wedged service runtime silently took scrapes down). A `sync_channel` hand-off makes init fail-fast and guarantees the global recorder is installed before init returns; a new integration test pins the runtime-free (da-watcher-shaped) caller end-to-end with a raw TcpStream scrape. Also binds the executor's exporter on `0.0.0.0:9004` in the Nomad job so the chaos suite can (per the commit message) probe it over the cluster bridge instead of via `docker exec`.

## Findings

### F03.1 [medium] [logic] — Claimed bridge-probe change is not implemented; EXECUTOR_IPS is dead code
- **Where**: deploy/cluster/scripts/chaos.sh:101-102 (at the commit and at HEAD); executor_progress at chaos.sh:247-262, sealer_boundaries at chaos.sh:148-162 (HEAD)
- **What**: The third PR commit's message ("probe executor metrics directly over the bridge, not via docker exec") says chaos.sh "probes http://<node_ip>:9004/metrics first, falling back to docker exec for loopback-only deploys". The actual chaos.sh change is only the `EXECUTOR_IPS=(192.168.56.41 ...)` array plus a comment — even the original branch commit (b388906) contains no probe change. `executor_progress()` and `sealer_boundaries()` still go exclusively through `timeout 8 docker exec ... curl 127.0.0.1:9004`, so `EXECUTOR_IPS` is never referenced and the very flake mechanism the commit identifies (dockerd stalling `docker exec` runner-wide after a privileged sibling kill) remains fully in the observation path. The `0.0.0.0:9004` bind in executor.nomad.hcl is therefore currently pointless.
- **Still present at HEAD**: yes
- **Suggested fix**: Either implement the probe as described (try `curl http://${EXECUTOR_IPS[i]}:9004/metrics` first, fall back to `docker exec`) or delete `EXECUTOR_IPS` and the `0.0.0.0` bind; as-is the commit message documents behavior that does not exist.

### F03.2 [low] [logic] — Exporter bind failure no longer fails init; it is only a background log line
- **Where**: crates/obs/src/lib.rs:88-101 (at the commit and HEAD)
- **What**: `ready_tx.send(Ok(()))` fires after `build()` and `set_global_recorder` succeed, but the HTTP listener actually binds when the exporter future is first polled inside `rt.block_on(exporter)` — after init has already returned Ok. A port-in-use (e.g. two services sharing `KARDAMOM_METRICS_ADDR`, a hazard observability.md explicitly warns about) yields a healthy-looking service with no `/metrics`, and the only evidence is one `tracing::error!` from the obs-exporter thread. The previous `install()` had a similar deferred-bind quality, so this is not a regression, but the new structure could have caught it: the ready hand-off is right there.
- **Still present at HEAD**: yes
- **Suggested fix**: Bind the listener eagerly (e.g. `PrometheusBuilder::with_http_listener` after a manual `TcpListener::bind` check, or await the exporter's first poll result) before sending `Ok(())` through `ready_tx`.

### F03.3 [nit] [logic] — Test's free-port pattern is TOCTOU-racy
- **Where**: crates/obs/tests/init_without_runtime.rs:17-22 (at the commit and HEAD)
- **What**: The test binds `127.0.0.1:0`, drops the listener, then has init rebind the same port. Another process (or a parallel test binary) can grab the port in the window, failing the test spuriously.
- **Still present at HEAD**: yes
- **Suggested fix**: Tolerable for a single-test file; could retry init on bind failure with a fresh port if it ever flakes.

## Verdict
The lib.rs change is careful and well-executed: the dedicated thread genuinely decouples scrape liveness from the service runtime, the builder-inside-the-runtime fix plus the sync_channel hand-off addresses the real da-watcher crash-loop regression from the first attempt, error paths all report through the channel, and the runtime-free integration test pins the exact caller shape that broke. The weak spot is the deploy/chaos half: the commit message narrates a probe-transport change (bridge-direct scrapes) that was never actually written, leaving a dead `EXECUTOR_IPS` array, an unused `0.0.0.0` exporter bind, and the docker-exec flake mechanism still live (F03.1).
